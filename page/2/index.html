《The Llama 3 Herd of Models》引言

发表于 2026-10-04 分类于 书籍翻译

1 引言

Introduction

Llama 3 模型群组

Llama Team, AI @ Meta¹

¹详细的贡献者名单见本文附录。

现代人工智能（AI）系统由基础模型驱动。本文介绍一组新的基础模型，称为 Llama 3。这是一个原生支持多语言、编码、推理和工具使用的语言模型群组。我们最大的模型是一个稠密 Transformer，拥有 405B 参数和最高 128K token 的上下文窗口。本文对 Llama 3 进行了广泛的实证评估。我们发现 Llama 3 在众多任务上提供了与 GPT-4 等领先语言模型相当的质量。我们公开发布了 Llama 3，包括预训练和后训练版本的 405B 参数语言模型，以及用于输入和输出安全的 Llama Guard 3 模型。本文还展示了通过组合方法将图像、视频和语音能力集成到 Llama 3 中的实验结果。我们观察到，这种方法在图像、视频和语音识别任务上与当前最优水平具有竞争力。这些模型仍在开发中，尚未广泛发布。

日期：2024 年 7 月 23 日

网站：https://llama.meta.com/

最近更新：2026-10-2

6.《AI Engineering: Building Applications with Foundation Models》（Chip Huyen）

本书在AI应用或者AI工程的视角上深入浅出地整体介绍了一遍，理论上是AI体系的数学基础、LLM原理之上的应用层面的书籍。不是那么技术，偏科普、偏宏观方面的书，很系统、很全面地介绍了LLM及其应用的一些原理和注意的事项。有点像整个AI软件工程的生命周期：架构设计、评估、安全护栏、成本控制、延迟优化、线上监控等等，偏向于“设计指南”和“架构蓝图”，教读者如何把一个大模型应用真正落地到生产环境。

总体上来说，本书是近期看到的一本很好的介绍大语言模型应用方面的好书，让读者能对整个AI的应用和宏观概念有个系统的理解，非常值得推荐。

普通读者的阅读顺序可以是1-2-6的顺序阅读这几本书。

《AI Engineering》读书心得

发表于 2026-10-02 分类于 读书心得（技术）

当时闹书荒，让AI推荐一本关于AI的书籍。当时有一本书，Gemini给它冠以这样的评价："如果只读一本关于AI的书籍，那就是《AI Engineering: Building Applications with Foundation Models》（Chip Huyen）。"当时觉得可能是广告，或者是AI的幻觉，不过细读之后，基本认同AI的这句断言。

唯一不足的地方是，因为成书于2024年、发售于2025年1月，在AI技术日新月异的情况下，一些新技术着墨不深，例如Agent的能力、MCP协议的工具调用、Skill的普及和高效。就像Skill（技能）已经实现了从"静态 Prompt"到"动态可插拔 Skill"的范式转变：通过按需检索并加载（Load / Unload）对应的 Skill，实现"无限扩展能力"而无需撑爆上下文窗口。

不过话说回来，尽管AI技术和模型日新月异，但书中的核心架构理念、设计权衡（Trade-offs）和方法论相对"永恒"，不会因为某个特定工具的过时而失效。

本书在AI应用或AI工程的视角上，确实深入浅出地整体介绍了一遍，理论上是AI体系的数学基础、LLM原理之上的应用层面的书籍。它不是那么技术，偏科普、偏宏观，书中很系统、全面地介绍了LLM及其应用的一些原理和注意事项。有点像AI整个软件工程的生命周期：架构设计、评估、安全护栏、成本控制、延迟优化、线上监控，偏向于"设计指南"和"架构蓝图"，教读者如何把一个大模型应用真正带入生产环境。

总体上来说，本书是近期看到的一本很好的介绍大语言模型应用方面的好书，让读者能对整个AI的应用和宏观概念有个系统的理解，非常值得推荐。

第10章 AI工程架构与用户反馈

Chapter 10. AI Engineering Architecture and User Feedback

迄今为止，本书介绍了大量将基础模型适配到特定应用的技术。本章将讨论如何将这些技术整合起来，构建成功的产品。

面对种类繁多的AI工程技术及工具，选择合适的方案可能令人不知所措。为简化这一过程，本章采取渐进式方法：从基础模型应用的最简单架构出发，指出该架构面临的挑战，然后逐步添加组件以应对这些挑战。

我们可以花无尽的时间来思考如何构建一个成功的应用，但验证一个应用是否真正实现了目标，唯一的方法就是将它交给用户使用。用户反馈对于指导产品开发一直至关重要，但对于AI应用而言，用户反馈作为改进模型的数据来源，其作用更为关键。对话式交互界面使用户更容易给出反馈，但也让开发者更难以从中提取信号。本章将讨论各类对话式AI反馈，以及如何设计一套系统，在不损害用户体验的前提下收集正确的反馈。

《AI Engineering》第9章推理优化

发表于 2026-09-29 分类于 书籍翻译

第9章 推理优化

Chapter 9. Inference Optimization

新模型层出不穷，但有一件事始终重要：让它们变得更好、更便宜、更快。到目前为止，本书已经讨论了各种让模型变得更好的技术。本章将聚焦于让模型变得更快、更便宜。无论你的模型有多好，如果它太慢，用户可能会失去耐心，更糟糕的是，其预测结果可能会变得毫无用处——想象一个隔夜股票价格预测模型需要两天时间计算每个结果。如果模型太贵，其投资回报率将得不偿失。

推理优化可以在模型、硬件和服务三个层面进行。在模型层面，你可以减小已训练模型的尺寸，或开发更高效的架构，例如消除Transformer模型中注意力机制的计算瓶颈。在硬件层面，你可以设计更强大的硬件。

推理服务在特定硬件上运行模型以处理用户请求。它可以结合针对特定硬件优化模型的技术，还需要考虑使用模式和流量模式，以高效分配资源，降低延迟和成本。

正因如此，推理优化是一个跨学科领域，通常需要模型研究人员、应用开发者、系统工程师、编译器设计者、硬件架构师甚至数据中心运营者之间的协作。

本章讨论AI推理的瓶颈以及克服这些瓶颈的技术。它主要关注模型和服务层面的优化，并概述AI加速器。

  1. 如第7章所述，推理只涉及前向传播，而训练同时涉及前向和反向传播。
  2. 我的朋友Mark Saroufim向我指出了模型训练成本和推理成本之间的一个有趣关系。假设你是模型提供商。令T为总训练成本，p为每次推理的收费，N为可售出的推理调用次数。开发一个模型只有在从推理中回收的资金超过其训练成本时才划算，即T ≤ p × N。一个模型在生产中使用得越多，模型提供商就越能降低推理成本。然而，这不适用于在开源模型之上销售推理调用的第三方API提供商。

本章还涵盖了性能指标和权衡。有时，加速模型的技术也能降低成本。例如，降低模型精度使其更小、更快。但优化通常需要权衡。例如，最好的硬件可能让模型运行更快，但成本更高。

随着开源模型越来越丰富，越来越多的团队在构建自己的推理服务。然而，即使你不实现这些推理优化技术，理解这些技术也能帮助你评估推理服务和框架。如果你的应用延迟和成本让你困扰，请继续往下读。本章或许能帮你诊断原因并找到潜在解决方案。

《AI Engineering》第8章数据集工程

发表于 2026-09-28 分类于 书籍翻译

第8章 数据集工程

Chapter 8. Dataset Engineering

数据的日益重要性体现在从GPT-3到GPT-4数据工作量的变化上。在GPT-3（OpenAI, 2020）的贡献者名单中，只有两人被标注为负责数据收集、过滤、去重以及对训练数据进行重叠分析。三年后，这一情况发生了巨大变化。对于GPT-4（OpenAI, 2023），有八十人因参与不同的数据处理工作而被列入名单。这还不包括OpenAI通过数据提供商外包的数据标注人员。对于像ChatML格式这样听起来简单的工作，就有十一人参与，其中许多是资深研究员。在OpenAI 2016年的AMA（有问必答）帖中，联合创始人Wojciech Zaremba曾表示，他们打算主要使用公开数据集进行研究。

模型的质量取决于其训练数据的质量。世界上最好的ML团队，即使拥有无限的计算资源，如果你没有数据，也无法帮你微调出一个好模型。数据集工程的目标是创建能够让你训练出最佳模型的数据集，理想情况下是在分配的预算内完成。

随着能够负担从头开发模型的公司越来越少，越来越多的企业转向通过数据来差异化其AI性能。随着模型对数据的需求不断增长，数据处理变得更加具有挑战性，需要更多的人才和基础设施投入。¹

数据操作已从人们有空时才处理的附带任务演变为专门岗位。许多AI公司现在雇佣数据标注员、数据集创建者和数据质量工程师，他们或融入核心工程团队，或与之并肩工作。

如果说模型领域的众多产品已经让人眼花缭乱，那么数据领域则更为复杂，不断涌现出越来越多的数据集和技术。本章将为你概述数据领域的情况，以及在构建自己的数据集时需要考虑的因素。

首先从数据策展开始，讨论需要什么样的数据、需要多少数据、高质量数据意味着什么等问题。然后介绍数据合成和处理的技术。数据策展、生成和处理并非线性流程。你可能需要在不同步骤之间反复迭代。

对于同一个模型，不同的训练阶段旨在教会模型不同的能力，因此需要具有不同属性的数据集。例如，预训练的数据量通常以token数量衡量，而监督微调的数据量通常以样本数量衡量。不过，在高层次上，它们的策展流程遵循相同的原则。本章重点讨论训练后数据，因为这与应用开发者更为相关。同时，当预训练数据的经验对训练后数据有启发时，我也会一并纳入。

发表于 2026-09-27 分类于 书籍翻译

第7章 微调

Chapter 7. Finetuning

微调（Finetuning）是指通过在完整模型或部分模型上进行进一步训练，使模型适应特定任务的过程。第5章和第6章讨论了基于提示的方法，这些方法通过给模型提供指令、上下文和工具来使其适配。而微调则是通过调整模型的权重来适配模型。

微调可以提升模型的多个方面。它可以增强模型的领域特定能力，例如编程或医学问答，也可以加强模型的安全性。然而，微调最常用于改进模型的指令遵循能力，特别是确保模型遵循特定的输出风格和格式。

虽然微调有助于创建更符合你需求的定制化模型，但它也需要更多的初始投入。我经常听到的一个问题是：何时应该微调，何时应该使用RAG。在对微调进行概述之后，本章将讨论微调的理由和不微调的理由，以及一个简单的框架来思考如何在微调和替代方法之间做出选择。

与基于提示的方法相比，微调的内存占用要高得多。在当代基础模型的规模下，朴素的微调通常需要超过单块GPU可用内存的容量。这使得微调既昂贵又具有挑战性。正如本章所讨论的，减少内存需求是众多微调技术的主要动机。本章专门用一节来概述影响模型内存占用的因素，这对于理解这些技术至关重要。

在微调领域，一种占据主导地位的内存高效方法是PEFT（参数高效微调，Parameter-Efficient Finetuning）。本章探讨了PEFT及其与传统微调的区别；本章还概述了其不断演进的技术。我将特别关注其中一个引人注目的类别：基于适配器（adapter）的技术。

对于基于提示的方法，了解ML模型在底层如何运行是推荐但不强制要求的。然而，微调带你进入了模型训练的领域，这里需要ML知识。ML基础超出了本书的范围。如果你想要快速复习一下，本书的GitHub仓库提供了有用资源的指引。在本章中，我将介绍一些与讨论直接相关的核心概念。

本章对我来说是写作上最具技术挑战性的一章，不是因为概念的复杂性，而是因为这些概念涵盖的广泛范围。我猜想阅读起来也可能具有技术挑战性。如果在任何时候你觉得自己在深入钻研与工作无关的细节，可以随时跳过。有很多内容要讨论。让我们开始吧！

第6章 RAG与智能体

Chapter 6. RAG and Agents

要解决一个任务，模型既需要知道如何执行任务的指令，也需要完成任务所必需的信息。就像人类在缺乏信息时更容易给出错误答案一样，AI 模型在缺少上下文时也更容易犯错和产生幻觉。对于特定应用而言，模型的指令对所有查询都是通用的，而上下文则是每个查询所特有的。上一章讨论了如何为模型编写良好的指令。本章将聚焦于如何为每个查询构建相关的上下文。

构建上下文的两种主导模式是 RAG（检索增强生成，Retrieval-Augmented Generation）和智能体（Agent）。RAG 模式允许模型从外部数据源检索相关信息。智能体模式则允许模型使用诸如网络搜索和新闻 API 等工具来收集信息。

RAG 模式主要用于构建上下文，而智能体模式能做的远不止于此。外部工具可以帮助模型弥补自身的不足并扩展其能力。最重要的是，它们赋予了模型直接与世界交互的能力，使得模型能够自动化我们生活的许多方面。RAG 和智能体模式都令人兴奋，因为它们为本就强大的模型带来了新的能力。在短短的时间内，它们就成功捕捉了集体想象力，催生了令人惊叹的演示和产品，让许多人相信它们就是未来。本章将详细介绍这两种模式、它们的工作原理以及它们的 promising 之处。

第5章 提示工程

Chapter 5. Prompt Engineering

提示工程（Prompt Engineering）指设计指令以引导模型生成期望输出的过程。提示工程是最简单、最常见的一种模型适配技术。与微调不同，提示工程通过引导模型行为，而不改变模型的权重。得益于基础模型强大的底层能力，许多人仅通过提示工程就成功地将模型适配到了实际应用中。在转向微调等资源密集型技术之前，你应充分利用提示工程。

提示工程的易用性容易让人误以为它没有什么门道。¹ 乍一看，提示工程似乎不过是摆弄措辞直到有效为止。虽然提示工程确实涉及大量试错，但它也包含许多有趣的挑战和精巧的解决方案。你可以将提示工程视为人机沟通：你与AI模型沟通，让它们按你的意愿行事。每个人都能沟通，但并非每个人都能有效沟通。同样，写提示很容易，但写出有效的提示并不容易。

有些人认为"提示工程"缺乏成为一门工程学科的严谨性。然而，这并非必然如此。提示实验应当以与任何机器学习实验相同的严谨性来开展——包括系统性的实验和评估。

提示工程的重要性被一位我采访过的OpenAI研究经理精辟地总结道："问题不在于提示工程。它是一项真实且有用的技能。问题在于当提示工程是人们唯一懂得的东西。"要构建生产级的AI应用，你需要的远不止提示工程。你需要统计学、工程学和经典的机器学习知识，来进行实验跟踪、评估和数据集管理。

本章涵盖如何编写有效提示，以及如何保护你的应用免受提示攻击。在深入探讨你可以用提示构建的各种有趣应用之前，让我们先了解一些基础知识，包括提示究竟是什么以及提示工程的最佳实践。

第4章 评估AI系统

Evaluate AI Systems

一个模型只有在为其预期目的工作时才有用。你需要在你的应用场景中评估模型。第3章讨论了自动评估的不同方法。本章讨论如何使用这些方法来评估适用于你应用的模型。

本章包含三个部分。首先讨论你可能用于评估应用的标准，以及这些标准如何被定义和计算。例如，许多人担心AI编造事实——事实一致性（factual consistency）是如何检测的？数学、科学、推理和摘要等领域特定能力是如何度量的？

第二部分聚焦于模型选择。面对越来越多的基础模型可供选择，为你的应用选择正确的模型可能会让人感到不知所措。已有数千个基准测试被引入，用于根据不同标准评估这些模型。这些基准测试可信吗？如何选择要使用的基准测试？聚合多个基准测试结果的公开排行榜又如何？

模型领域充斥着专有模型和开源模型。许多团队需要反复面对的一个问题是：是自行托管模型还是使用模型API。随着基于开源模型的模型API服务的引入，这个问题变得更加微妙。

最后一部分讨论如何开发一个评估流水线（evaluation pipeline），以长期指导你的应用的开发。这部分汇集了本书中学习到的技术，用于评估具体的应用。
