《The Llama 3 Herd of Models》3 预训练

发表于 2026-10-04 分类于 书籍翻译

3 预训练

Pre-Training

语言模型预训练包括：(1) 大规模训练语料的策划与过滤；(2) 模型架构的研发及相应的用于确定模型规模的缩放法则；(3) 大规模高效预训练技术的开发；(4) 预训练方案的制定。下面我们将分别介绍这些组成部分。

3.1 预训练数据

Pre-Training Data

我们通过多种数据来源为语言模型预训练创建数据集，这些数据包含截至 2023 年底的知识。我们对每个数据来源应用多种去重方法和数据清洗机制，以获得高质量的 token。我们移除包含大量个人可识别信息（PII）的域名，以及已知包含成人内容的域名。

3.1.1 网络数据策展

Web Data Curation

我们使用的数据大部分来自网络，以下描述我们的清洗流程。

PII 与安全过滤。 除其他缓解措施外，我们实施了过滤器，旨在移除来自以下网站的数据：可能包含不安全内容或大量 PII 的网站、根据 Meta 多项安全标准被认定为有害的域名，以及已知包含成人内容的域名。

文本提取与清洗。 我们处理非截断网络文档的原始 HTML 内容，以提取高质量且多样化的文本。为此，我们构建了一个自定义解析器，用于提取 HTML 内容，并在样板移除的精确性和内容召回率方面进行优化。我们通过人工评估来评价解析器的质量，并将其与优化用于提取文章类内容的流行的第三方 HTML 解析器进行比较，发现我们的解析器表现更优。我们仔细处理包含数学和代码内容的 HTML 页面，以保留这些内容的结构。我们保留了图像的 alt 属性文本，因为数学内容通常以预渲染图像的形式呈现，而数学公式也同时包含在 alt 属性中。我们通过实验评估了不同的清洗配置。我们发现，与纯文本相比，markdown 对主要基于网络数据训练的模型性能有害，因此我们移除了所有 markdown 标记。

去重。 我们在 URL、文档和行级别应用了多轮去重：

  • URL 级别去重。 我们在整个数据集上执行 URL 级别的去重。对于每个 URL 对应的页面，我们保留最新的版本。
  • 文档级别去重。 我们在整个数据集上执行全局 MinHash（Broder, 1997）去重，以移除近似重复的文档。
  • 行级别去重。 我们执行类似于 ccNet（Wenzek et al., 2019）的激进的行级别去重。我们移除在每桶 3000 万文档中出现超过 6 次的行。尽管我们的人工定性分析显示，行级别去重不仅移除了来自各种网站的残余样板内容（如导航菜单、Cookie 警告），也会移除频繁出现的高质量文本，但我们的实证评估显示其带来了显著的改进。

启发式过滤。 我们开发了启发式方法，用于移除额外的低质量文档、异常值和过度重复的文档。一些启发式方法的示例包括：

  • 我们使用重复 n-gram 覆盖率（Rae et al., 2021）来移除由重复内容（如日志或错误信息）组成的行。这些行可能非常长且独特，因此无法通过行去重过滤。
  • 我们使用"脏词"计数（Raffel et al., 2020）来过滤未被域名屏蔽列表覆盖的成人网站。
  • 我们使用 token 分布的 Kullback-Leibler 散度来过滤包含与训练语料分布相比异常 token 过多的文档。

基于模型的质量过滤。 此外，我们尝试应用多种基于模型的质量分类器来子选择高质量 token。这包括使用诸如 fasttext（Joulin et al., 2017）等快速分类器，训练其识别给定文本是否会被维基百科引用（Touvron et al., 2023a），以及使用基于 Llama 2 预测训练的、计算密集度更高的 Roberta 分类器（Liu et al., 2019a）。为了训练基于 Llama 2 的质量分类器，我们创建了一个由清洗后的网络文档组成的训练集，描述了质量要求，并指示 Llama 2 的聊天模型判断文档是否满足这些要求。出于效率考虑，我们使用 DistilRoberta（Sanh et al., 2019）为每个文档生成质量分数。我们通过实验评估了各种质量过滤配置的有效性。

代码与推理数据。 与 DeepSeek-AI et al.（2024）类似，我们构建了特定领域的流水线，用于提取与代码和数学相关的网页。具体来说，代码和推理分类器都是 DistilRoberta 模型，在由 Llama 2 标注的网络数据上训练。与上述通用质量分类器不同，我们进行了提示调优，以针对包含数学推导、STEM 领域推理以及与自然语言交错的代码的网页。由于代码和数学的 token 分布与自然语言有显著差异，这些流水线实现了领域特定的 HTML 提取、定制的文本特征和过滤启发式方法。

多语言数据。 与我们上述针对英语的处理流水线类似，我们实施了过滤器，用于移除可能包含 PII 或不安全内容的网站的数据。我们的多语言文本处理流水线具有若干独特特征：

  • 我们使用基于 fasttext 的语言识别模型将文档归类为 176 种语言。
  • 我们在每种语言的数据内部执行文档级和行级去重。
  • 我们应用语言特定的启发式方法和基于模型的过滤器来移除低质量文档。

此外，我们使用基于多语言 Llama 2 的分类器对多语言文档进行质量排序，以确保高质量内容获得优先处理。我们通过实验确定预训练中使用的多语言 token 数量，平衡模型在英语和多语言基准上的性能。

3.1.2 确定数据混合比例

Determining the Data Mix

要获得高质量的语言模型，必须仔细确定预训练数据混合中不同数据来源的比例。我们确定数据混合比例的主要工具是知识分类和缩放法则实验。

知识分类。 我们开发了一个分类器，对网络数据中包含的信息类型进行分类，以便更有效地确定数据混合比例。我们使用该分类器对网络上过度呈现的数据类别（例如，艺术与娱乐）进行降采样。

数据混合的缩放法则。 为了确定最佳的数据混合比例，我们进行了缩放法则实验，在实验中我们使用某种数据混合训练若干小模型，并利用结果预测大模型在该混合上的表现（见第 3.2.1 节）。我们对不同的数据混合比例重复此过程多次，以选择新的候选数据混合。随后，我们在此候选数据混合上训练一个更大的模型，并在若干关键基准上评估该模型的性能。

数据混合总结。 我们最终的数据混合大约包含 50% 对应通用知识的 token、25% 的数学和推理 token、17% 的代码 token 以及 8% 的多语言 token。

3.1.3 退火数据

Annealing Data

根据经验，我们发现使用少量高质量代码和数学数据进行退火（见第 3.4.3 节）可以提升预训练模型在关键基准上的表现。与 Li et al.（2024b）类似，我们使用一种对选定领域的高质量数据进行上采样的数据混合来执行退火。我们未在退火数据中包含任何来自常用基准训练集的数据。这使我们能够评估 Llama 3 真正的少样本学习能力和域外泛化能力。

个人注：这里的“退火”借用了冶金学里的概念，在大模型训练中指的是一种学习率调度策略，核心是：在预训练接近尾声时，把学习率降得很低，同时换用少量高质量数据，让模型“精修”一下。

冶金学里的“退火”：金属加热后缓慢冷却，能消除内部应力、让结构更稳定、性能更好。关键词是：先高温，后缓慢降温。

参考 OpenAI（2023a），我们评估了在退火过程中使用 GSM8k（Cobbe et al., 2021）和 MATH（Hendrycks et al., 2021b）训练集进行退火的效果。我们发现，退火使预训练的 Llama 3 8B 模型在 GSM8k 和 MATH 验证集上的性能分别提升了 24.0% 和 6.4%。然而，405B 模型的改进微乎其微，这表明我们的旗舰模型具有较强的上下文学习和推理能力，不需要特定的域内训练样本即可获得优异表现。

使用退火评估数据质量。 与 Blakeney et al.（2024）类似，我们发现退火使我们能够判断小型领域特定数据集的价值。我们通过将训练了 50% 的 Llama 3 8B 模型的学习率在 400 亿 token 上线性退火至 0 来评估此类数据集的价值。在这些实验中，我们赋予新数据集 30% 的权重，其余 70% 的权重分配给默认数据混合。对于每个小数据集，使用退火来评估新数据源比执行缩放法则实验更高效。

3.2 模型架构

Model Architecture

Llama 3 使用标准的密集 Transformer 架构（Vaswani et al., 2017）。在模型架构方面，它与 Llama 和 Llama 2（Touvron et al., 2023a,b）没有显著差异；我们的性能提升主要源于数据质量和多样性的改进，以及训练规模的扩大。

与 Llama 2 相比，我们做了几项小改动：

  • 我们使用分组查询注意力（GQA；Ainslie et al.（2023）），采用 8 个键值头，以提高推理速度并减少解码过程中键值缓存的大小。
  • 我们使用一种注意力掩码，防止同一序列中不同文档之间的自注意力。我们发现这一改动在标准预训练期间影响有限，但在超长序列的持续预训练中很重要。
  • 我们使用包含 128K token 的词表。我们的 token 词表将 tiktoken³ 分词器的 100K token 与额外 28K 用于更好支持非英语语言的 token 相结合。与 Llama 2 分词器相比，我们的新分词器在英语数据样本上的压缩率从每个 token 3.17 个字符提高到 3.94 个字符。这使得模型能够在相同的训练计算量下"阅读"更多文本。我们还发现，从选定的非英语语言中添加 28K token 既提高了压缩率，也提升了下游性能，且对英语分词没有影响。
  • 我们将 RoPE 基频超参数增加到 500,000。这使得我们能够更好地支持更长的上下文；Xiong et al.（2023）表明该值对于最长 32,768 的上下文长度是有效的。

Llama 3 405B 采用包含 126 层、token 表示维度为 16,384 以及 128 个注意力头的架构；详情见表 3。根据我们训练预算为 3.8 × 10²⁵ FLOPs 的数据上的缩放法则，这使得模型规模大致达到计算最优。

3.2.1 缩放法则

Scaling Laws

我们开发了缩放法则（Hoffmann et al., 2022；Kaplan et al., 2020），以根据我们的预训练计算预算确定旗舰模型的最优规模。除了确定最优模型规模外，一个主要挑战是预测旗舰模型在下游基准任务上的性能，这涉及几个问题：(1) 现有的缩放法则通常只预测下一个 token 预测损失，而非特定的基准性能。(2) 缩放法则可能噪声大且不可靠，因为它们是基于小计算预算下的预训练运行开发的（Wei et al., 2022b）。

为应对这些挑战，我们实施了一个两阶段方法来开发能准确预测下游基准性能的缩放法则：

  1. 我们首先建立计算最优模型在下游任务上的负对数似然与训练 FLOPs 之间的相关性。
  2. 接着，我们利用缩放法则模型和使用更高计算 FLOPs 训练的较早模型，将下游任务上的负对数似然与任务准确率关联起来。在此步骤中，我们特别利用了 Llama 2 模型家族。

这种方法使我们能够针对特定数量的训练 FLOPs 预测计算最优模型的下游任务性能。我们使用类似的方法来选择我们的预训练数据混合（见第 3.4 节）。

缩放法则实验。 具体来说，我们通过在 6 × 10¹⁸ FLOPs 到 10²² FLOPs 之间的计算预算下预训练模型来构建缩放法则。在每个计算预算下，我们预训练大小在 40M 到 16B 参数之间的模型，在每个计算预算下使用部分模型大小。在这些训练运行中，我们使用余弦学习率调度，并配备 2,000 个训练步骤的线性预热。峰值学习率根据模型大小设置在 2 × 10⁻⁴ 到 4 × 10⁻⁴ 之间。我们将余弦衰减设定为峰值的 0.1。每一步的权重衰减设置为该步学习率的 0.1 倍。对于每个计算规模，我们使用固定的批次大小，范围在 250K 到 4M 之间。

预测下游任务性能。 我们使用由此产生的计算最优模型来预测旗舰 Llama 3 模型在基准数据集上的性能。首先，我们建立（归一化的）基准中正确答案的负对数似然与训练 FLOPs 之间的线性相关性。在此分析中，我们仅使用在所述数据混合上训练至 10²² FLOPs 的缩放法则模型。接着，我们利用缩放法则模型和 Llama 2 模型（使用 Llama 2 数据混合和分词器训练）建立对数似然与准确率之间的 S 形关系。我们在 ARC Challenge 基准上展示了这一实验的结果（图 4）。我们发现这种跨越四个数量级外推的两步缩放法则预测相当准确：它仅略微低估了旗舰 Llama 3 模型的最终性能。

3.3 基础设施、扩展与效率

Infrastructure, Scaling, and Efficiency

我们描述了为 Llama 3 405B 大规模预训练提供动力的硬件和基础设施，并讨论了带来训练效率提升的多项优化。

3.3.1 训练基础设施

Training Infrastructure

Llama 1 和 Llama 2 模型是在 Meta 的 AI Research SuperCluster（Lee and Sengupta, 2022）上训练的。随着我们进一步扩展规模，Llama 3 的训练迁移到了 Meta 的生产集群（Lee et al., 2024）。这种设置针对生产级可靠性进行了优化，这对于我们扩展训练规模至关重要。

计算资源。 Llama 3 405B 在最多达 16K 块 H100 GPU 上进行训练，每块 GPU 运行在 700W TDP，配备 80GB HBM3 显存，使用 Meta 的 Grand Teton AI 服务器平台（Matt Bowman, 2022）。每台服务器配备 8 块 GPU 和 2 个 CPU。在服务器内部，8 块 GPU 通过 NVLink 连接。训练任务通过 MAST（Choudhury et al., 2024）——Meta 的全球级训练调度器——进行调度。

存储。 Tectonic（Pan et al., 2021），Meta 的通用分布式文件系统，被用于为 Llama 3 预训练构建存储架构（Battey and Gupta, 2024）。它提供来自 7,500 台配备 SSD 的服务器的 240 PB 存储容量，并支持 2 TB/s 的持续吞吐量和 7 TB/s 的峰值吞吐量。一个主要挑战是支持高度突发性的检查点写入，这些写入会在短时间内饱和存储架构。检查点保存每块 GPU 的模型状态，每块 GPU 的范围为 1 MB 到 4 GB，用于恢复和调试。我们旨在最小化检查点期间的 GPU 暂停时间，并增加检查点频率以减少恢复后丢失的工作量。

网络。 Llama 3 405B 使用了基于 Arista 7800 和 Minipack2 Open Compute Project⁴ OCP 机架交换机的 RDMA over Converged Ethernet（RoCE）架构。Llama 3 系列中较小的模型使用 Nvidia Quantum2 InfiniBand 架构进行训练。RoCE 和 InfiniBand 集群都利用 GPU 之间的 400 Gbps 互连。尽管这些集群在底层网络技术方面存在差异，但我们对两者都进行了调优，使其在这些大规模训练工作负载上提供同等的性能。由于我们完全拥有其设计，我们将进一步详细阐述我们的 RoCE 网络。

⁴Open Compute Project：https://www.opencompute.org/

  • 网络拓扑。 我们的基于 RoCE 的 AI 集群包含 24K 块 GPU⁵，通过三层 Clos 网络（Lee et al., 2024）连接。在底层，每个机架托管 16 块 GPU，分布在两台服务器之间，并通过一个 Minipack2 架顶（ToR）交换机连接。在中间层，192 个这样的机架通过集群交换机连接，形成一个拥有 3,072 块 GPU 且具有全二分带宽的 pod，确保无超分。在顶层，同一数据中心建筑内的 8 个此类 pod 通过汇聚交换机连接，形成一个 24K GPU 的集群。然而，汇聚层的网络连接并未保持全二分带宽，而是具有 1:7 的超分比。我们的模型并行方法（见第 3.3.2 节）和训练任务调度器（Choudhury et al., 2024）都针对网络拓扑感知进行了优化，旨在最小化跨 pod 的网络通信。

⁵请注意，我们在 Llama 3 预训练中仅使用这 24K GPU 中的最多 16K。

  • 负载均衡。 LLM 训练会产生巨大的网络流量，难以使用传统方法（如等价多路径（ECMP）路由）在所有可用网络路径上进行负载均衡。为应对这一挑战，我们采用了两种技术。首先，我们的集合通信库在两个 GPU 之间创建 16 条网络流，而非仅一条，从而减少每条流的流量并提供更多流用于负载均衡。其次，我们的增强型 ECMP（E-ECMP）协议通过哈希数据包 RoCE 头部中的额外字段，有效地将这 16 条流均衡分布到不同的网络路径上。
  • 拥塞控制。 我们在 spine 层使用深缓冲交换机（Gangidi et al., 2024），以容纳由集合通信模式引起的瞬时拥塞和缓冲。这种设置有助于限制持久拥塞和由慢速服务器引起的网络背压的影响，这在训练中很常见。最后，通过 E-ECMP 实现更好的负载均衡显著减少了拥塞的可能性。凭借这些优化，我们成功地在没有使用数据中心量化拥塞通知（DCQCN）等传统拥塞控制方法的情况下运行了一个 24K GPU 集群。

3.3.2 模型扩展的并行策略

Parallelism for Model Scaling

为了扩展我们最大模型的训练规模，我们使用了 4D 并行——四种不同并行方法的组合——来分片模型。这种方法高效地将计算分布到众多 GPU 上，并确保每块 GPU 的模型参数、优化器状态、梯度和激活值都能容纳在其 HBM 中。我们的 4D 并行实现如图 5 所示。它结合了张量并行（TP；Krizhevsky et al.（2012）；Shoeybi et al.（2019）；Korthikanti et al.（2023））、流水线并行（PP；Huang et al.（2019）；Narayanan et al.（2021）；Lamy-Poirier（2023））、上下文并行（CP；Liu et al.（2023a））和数据并行（DP；Rajbhandari et al.（2020）；Ren et al.（2021）；Zhao et al.（2023b））。

张量并行将单个权重张量分割成多个块，分布在不同的设备上。流水线并行将模型按层垂直划分为多个阶段，使得不同设备可以并行处理完整模型流水线的不同阶段。上下文并行将输入上下文分割成多个段，减少超长序列输入的内存瓶颈。我们使用全分片数据并行（FSDP；Rajbhandari et al., 2020；Ren et al., 2021；Zhao et al., 2023b），它对模型、优化器和梯度进行分片，同时实现数据并行——在多个 GPU 上并行处理数据并在每个训练步骤后同步。我们在 Llama 3 中使用 FSDP 对优化器状态和梯度进行分片，但对于模型分片，我们在前向计算后不重新分片，以避免反向传播过程中额外的 all-gather 通信。

流水线并行改进。 我们在现有实现中遇到了几个挑战：

  • 批次大小约束。 现有实现对每 GPU 支持的批次大小有限制，要求其能被流水线阶段数整除。对于图 6 中的示例，流水线并行的深度优先调度（DFS；Narayanan et al.（2021））要求 N = PP = 4，而广度优先调度（BFS；Lamy-Poirier（2023））要求 N = M，其中 M 是微批次的总体数量，N 是同一阶段前向或后向的连续微批次数量。然而，预训练通常需要灵活调整批次大小。
  • 内存不平衡。 现有的流水线并行实现会导致资源消耗不平衡。第一阶段由于嵌入层和预热微批次，消耗更多内存。
  • 计算不平衡。 在模型的最后一层之后，我们需要计算输出和损失，使得这一阶段成为执行延迟的瓶颈。

图 5：4D 并行示意图。GPU 按照 [TP, CP, PP, DP] 的顺序划分为并行组，其中 DP 代表 FSDP。在本示例中，16 块 GPU 的配置组大小为 |TP|=2、|CP|=2、|PP|=2 和 |DP|=2。GPU 在 4D 并行中的位置表示为向量 [D1, D2, D3, D4]，其中 Di 是第 i 个并行维度上的索引。在本例中，GPU0[TP0, CP0, PP0, DP0] 和 GPU1[TP1, CP0, PP0, DP0] 属于同一 TP 组，GPU0 和 GPU2 属于同一 CP 组，GPU0 和 GPU4 属于同一 PP 组，GPU0 和 GPU8 属于同一 DP 组。

为解决这些问题，我们修改了流水线调度方案，如图 6 所示，该方案允许灵活设置 N——在此例中 N = 5，可以在每个批次中运行任意数量的微批次。这使我们能够：(1) 在大规模下受限于批次大小时，运行比阶段数更少的微批次；或 (2) 运行更多微批次以隐藏点对点通信，从而在 DFS 和 BFS 之间找到通信效率和内存效率的最佳平衡点。为平衡流水线，我们分别从第一阶段和最后阶段各减少一个 Transformer 层。这意味着第一阶段上的第一个模型块仅包含嵌入层，最后阶段上的最后一个模型块仅包含输出投影和损失计算。为减少流水线气泡，我们使用交错调度（Narayanan et al., 2021），每个流水线 rank 上包含 V 个流水线阶段。整体流水线气泡比例为 PP−1 / (V × M)。此外，我们在 PP 中采用异步点对点通信，这显著加速了训练，尤其是在文档掩码引入额外计算不平衡的情况下。我们启用 TORCH_NCCL_AVOID_RECORD_STREAMS 来减少异步点对点通信带来的内存使用。最后，为降低内存成本，基于详细的内存分配分析，我们主动释放不会用于后续计算的张量，包括每个流水线阶段的输入和输出张量以及不会用于后续计算的张量。凭借这些优化，我们可以在不使用激活检查点的情况下，在 8K token 的序列上预训练 Llama 3。

长序列的上下文并行。 我们利用上下文并行（CP）来提高扩展 Llama 3 上下文长度时的内存效率，并支持训练最长 128K 的超长序列。在 CP 中，我们沿序列维度进行划分，具体来说，我们将输入序列划分为 2 × CP 个块，使每个 CP rank 接收两个块以实现更好的负载均衡。第 i 个 CP rank 同时接收第 i 块和第 (2 × CP − 1 − i) 块。

与采用环形结构重叠通信和计算的现有 CP 实现（Liu et al., 2023a）不同，我们的 CP 实现采用基于 all-gather 的方法：我们首先 all-gather 键（K）和值（V）张量，然后为本地查询（Q）张量块计算注意力输出。尽管 all-gather 通信延迟暴露在关键路径中，但我们仍然采用这种方法，主要有两个原因：(1) 在基于 all-gather 的 CP 注意力中，更容易且更灵活地支持不同类型的注意力掩码，例如文档掩码；(2) 暴露的 all-gather 延迟很小，因为由于使用 GQA（Ainslie et al., 2023），通信的 K 和 V 张量比 Q 张量小得多。因此，注意力计算的时间复杂度比 all-gather 高一个数量级（O(S²) 对比 O(S)，其中 S 表示完整因果掩码中的序列长度），使得 all-gather 开销可以忽略不计。

网络感知的并行配置。 并行维度的顺序 [TP, CP, PP, DP] 是针对网络通信优化的。最内层的并行需要最高的网络带宽和最低的延迟，因此通常限制在同一台服务器内。最外层的并行可能跨越多跳网络，应能容忍更高的网络延迟。因此，基于网络带宽和延迟的要求，我们按 [TP, CP, PP, DP] 的顺序排列并行维度。DP（即 FSDP）是最外层的并行，因为它可以通过异步预取分片的模型权重和规约梯度来容忍更长的网络延迟。在避免 GPU 内存溢出的同时，确定具有最小通信开销的最优并行配置是具有挑战性的。我们开发了一个内存消耗估算器和一个性能预测工具，帮助我们探索各种并行配置，预测整体训练性能，并有效识别内存缺口。

数值稳定性。 通过比较不同并行设置下的训练损失，我们修复了影响训练稳定性的若干数值问题。为确保训练收敛，我们在反向计算中使用 FP32 梯度累积跨多个微批次，并在 FSDP 中的数据并行工作节点间以 FP32 进行 reduce-scatter 梯度。对于在前向计算中被多次使用的中间张量（例如视觉编码器输出），其反向梯度也以 FP32 累积。

3.3.3 集合通信

Collective Communication

我们用于 Llama 3 的集合通信库基于 Nvidia NCCL 库的一个分支，称为 NCCLX。NCCLX 显著提升了 NCCL 的性能，特别是在高延迟网络环境下。回顾一下，并行维度的顺序是 [TP, CP, PP, DP]，其中 DP 对应 FSDP。最外层的并行维度 PP 和 DP 可能通过多跳网络通信，延迟高达数十微秒。原始的 NCCL 集合操作——FSDP 中的 all-gather 和 reduce-scatter，以及 PP 中的点对点通信——需要数据分块和阶段性数据拷贝。这种方法存在若干低效问题，包括 (1) 需要通过网络交换大量小型控制消息来协调数据传输，(2) 额外的内存拷贝操作，以及 (3) 将额外的 GPU 周期用于通信。对于 Llama 3 训练，我们通过调整分块和数据处理以适配我们的网络延迟（对于大型集群，可能高达数十微秒），解决了其中的部分低效问题。我们还允许小型控制消息以更高优先级穿越我们的网络，特别是在深缓冲核心交换机中避免队头阻塞。我们正在为未来 Llama 版本进行的工作包括在 NCCLX 中进行更深层次的更改，以全面解决上述所有问题。

3.3.4 可靠性与运营挑战

Reliability and Operational Challenges

16K GPU 训练的复杂性和潜在故障场景超过了我们运营过的规模更大的 CPU 集群。此外，训练的同步性质使其容错性较差——单个 GPU 故障可能需要重启整个作业。尽管面临这些挑战，在 Llama 3 中，我们实现了超过 90% 的有效训练时间，同时支持自动化集群维护（如固件和 Linux 内核升级（Vigraham and Leonhardi, 2024）），这导致了每天至少一次训练中断。有效训练时间衡量的是在总经过时间中用于有效训练的时间。

在预训练的 54 天快照期内，我们共经历了 466 次作业中断。其中 47 次是计划内中断，由自动化维护操作（如固件升级）或操作员发起的操作（如配置或数据集更新）导致。其余 419 次是意外中断，分类如表 5 所示。约 78% 的意外中断归因于已确认的硬件问题（如 GPU 或主机组件故障），或疑似硬件相关的问题（如静默数据损坏和非计划的单个主机维护事件）。GPU 问题是最大的类别，占所有意外问题的 58.7%。尽管故障数量较大，在此期间仅需三次重大人工干预，其余问题均由自动化处理。

为提高有效训练时间，我们减少了作业启动和检查点保存时间，并开发了用于快速诊断和问题解决的工具。我们广泛使用 PyTorch 内置的 NCCL 飞行记录器（Ansel et al., 2024），该功能将集合元数据和堆栈跟踪捕获到环形缓冲区中，从而允许我们在大规模下快速诊断挂起和性能问题，尤其是与 NCCLX 相关的问题。利用这一工具，我们高效地记录每个通信事件和每个集合操作的持续时间，并在 NCCLX 看门狗或心跳超时时自动转储跟踪数据。我们通过在线配置更改（Tang et al., 2015），在不需代码发布或作业重启的情况下，按需在生产环境中选择性启用计算密集度更高的跟踪操作和元数据收集。

大规模训练中的调试问题因我们的网络混合使用 NVLink 和 RoCE 而变得复杂。通过 NVLink 的数据传输通常通过 CUDA 内核发出的 load/store 操作进行，而远程 GPU 或 NVLink 连接的故障通常表现为 CUDA 内核中 stalled 的 load/store 操作，且未返回清晰的错误码。NCCLX 通过与 PyTorch 的紧密协同设计，增强了故障检测和定位的速度与准确性，使 PyTorch 能够访问 NCCLX 的内部状态并跟踪相关信息。虽然由 NVLink 故障引起的 stall 无法完全避免，但我们的系统会监控通信库的状态，并在检测到此类 stall 时自动超时。此外，NCCLX 跟踪每个 NCCLX 通信的内核和网络活动，并提供故障 NCCLX 集合的内部状态快照，包括所有 rank 之间已完成和待处理的数据传输。我们分析这些数据以调试 NCCLX 的扩展问题。

有时，硬件问题可能导致仍在运行但速度变慢的问题节点，这些节点难以检测。即使单个慢节点也能拖慢数千个其他 GPU，通常表现为通信正常但缓慢。我们开发了工具，用于优先处理来自选定进程组的潜在问题通信。通过仅调查少数几个主要嫌疑对象，我们通常能够有效识别出慢节点。

一个有趣的观察是环境因素对大规模训练性能的影响。对于 Llama 3 405B，我们注意到存在约 1-2% 的日内吞吐量波动，取决于具体时段。这种波动是午间较高温度影响 GPU 动态电压和频率调整的结果。

在训练过程中，数万块 GPU 可能同时增加或减少功耗，例如，由于所有 GPU 等待检查点保存或集合通信完成，或整个训练作业的启动或关闭。发生这种情况时，可能导致数据中心内功耗瞬时波动达到数十兆瓦级别，对电网容量构成挑战。随着我们为未来更大的 Llama 模型扩展训练规模，这仍是一个持续的挑战。

3.4 训练方案

Training Recipe

用于预训练 Llama 3 405B 的方案包含三个主要阶段：(1) 初始预训练，(2) 长上下文预训练，以及 (3) 退火。这三个阶段分别描述如下。我们使用类似的方案来预训练 8B 和 70B 模型。

3.4.1 初始预训练

Initial Pre-Training

我们使用 AdamW 预训练 Llama 3 405B，峰值学习率为 8 × 10⁻⁵，线性预热 8,000 步，余弦学习率调度在 1,200,000 步内衰减至 8 × 10⁻⁷。我们在训练早期使用较小的批次大小以提高训练稳定性，随后增加批次大小以提高效率。具体来说，我们使用初始批次大小为 400 万 token，序列长度为 4,096，在预训练 2.52 亿 token 后，将这些值翻倍为批次大小 800 万 token，序列长度 8,192。在预训练约 2.87T token 后，我们再次将批次大小翻倍至 1,600 万。我们发现该训练方案非常稳定：我们观察到很少的损失尖峰，且无需干预即可纠正模型训练发散。

调整数据混合。 我们在训练过程中对预训练数据混合进行了多次调整，以改善模型在特定下游任务上的表现。具体来说，我们在预训练期间增加了非英语数据的比例，以改善 Llama 3 的多语言性能。我们还上采样了数学数据，以提升模型的数学推理能力；在预训练后期添加了更多近期网络数据，以推进模型的知识截止日期；并对后来被识别为质量较低的预训练数据子集进行了降采样。

3.4.2 长上下文预训练

Long Context Pre-Training

在预训练的最后阶段，我们在长序列上进行训练，以支持最长 128K token 的上下文窗口。我们不更早地在长序列上训练，因为自注意力层中的计算量随序列长度呈二次增长。我们逐步增加支持的上下文长度，预训练直到模型成功适应增加后的上下文长度。我们通过衡量以下两方面来评估成功适应：(1) 短上下文评估上的模型性能已完全恢复；(2) 模型在该长度下完美解决了"大海捞针"任务。在 Llama 3 405B 预训练中，我们分六个阶段逐步增加上下文长度，从原始的 8K 上下文窗口开始，最终达到 128K 上下文窗口。此长上下文预训练阶段使用了约 8000 亿训练 token。

3.4.3 退火

Annealing

在最后 4000 万 token 的预训练过程中，我们将学习率线性退火至 0，同时保持 128K token 的上下文长度。在此退火阶段，我们还调整了数据混合，对高质量数据来源进行上采样；详见第 3.1.3 节。最后，我们在退火过程中计算模型检查点的平均值（Polyak (1991) 平均），以产生最终的预训练模型。
