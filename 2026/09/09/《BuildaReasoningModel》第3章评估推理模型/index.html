第 3 章 评估推理模型

Evaluating reasoning models

本章涵盖

  • 从 LLM 响应中可靠地提取最终答案
  • 通过将 LLM 的输出与参考解决方案进行比较，使用符号数学求解器验证答案的正确性
  • 运行一个完整的评估流水线，加载预训练模型，生成输出，并对照数据集进行评分

This chapter covers

  • Extracting final answers reliably from an LLM response

  • Verifying answer correctness by comparing an LLM’s output to the reference solution using a symbolic math solver

  • Running a full evaluation pipeline that loads a pretrained model, generates outputs, and grades them against a dataset

评估是我们区分那些仅仅听起来有说服力的 LLM 和那些能够正确解决问题的 LLM 的方法。LLM 评估技术涵盖了广泛的方法，从衡量任务准确性到确保 LLM 遵守特定的安全标准。在本章中，"评估"意味着在大量样本上定量测试模型，并将其输出与参考答案进行评分。

更具体地说，我们将重点实现一种基于验证的方法，通过使用类似计算器的实现，将 LLM 的答案与参考解决方案进行比较，从而检查 LLM 是否能准确解决数学问题。

这种验证器特别有用，因为它不仅评估了数学任务上的性能，还引入了可验证奖励（verifiable rewards）的原则，这是我们在第 6 章中将要实现的强化学习方法的基础。

图 3.1 本书所涵盖主题的模型图。本章介绍评估方法（第 2 阶段)，特别侧重于实现验证器，我们将在第 6 章中将其作为可验证奖励的基础进行复用。

3.1 构建数学验证器

Building a math verifier

评估训练后的 LLM 在实践中通常有四种常见方法：选择题、验证器、排行榜和 LLM 裁判。这些方法广泛用于研究论文、技术报告、营销材料和模型卡（即总结模型训练、评估及预期用途的文档），且评估结果通常来自多个类别的组合。

如图 3.1 所示，这些评估方法可以归为两大类：基准评估（benchmark-based evaluation）和判断评估（judgment-based evaluation）。前者通常更偏量化，后者则更依赖定性判断。这四种评估方法在不同场景下各有价值，但验证器对推理模型尤其重要。

数学问题是一个天然的示例：根据问题的复杂程度，它们适合分步推理，而评估过程却很简单，因为最终答案可以与正确答案直接比对。在此场景中，验证器提供了一种简单可靠的方式，用于衡量模型的推理步骤是否导向正确的结果。

在本章中，我们将聚焦于验证器，将其作为衡量数学问题解答正确性的基准评估方法。验证器将提取出的答案与参考答案进行比对（如图 3.2 所示），通常依赖代码解释器或计算程序等外部工具来完成。

注意 附录 F 涵盖其他评估方法，如选择题基准、基于偏好的排行榜以及 LLM 作为裁判的方法。

图 3.2  在自由形式问答中使用验证方法评估 LLM。模型生成一个自由形式的答案（可能包含多个推理步骤）和最终盒式答案，提取该答案后与数据集中的正确答案进行比较。

虽然我们当前的重点是评估，但验证器将在本书后续章节中再次出现。它们不仅用于衡量性能，还用作强化学习方法中的反馈信号来训练推理模型——这一点我们将在第 6 章中探讨。

验证器方法的缺点是，它只能应用于那些易于（最好是确定性）验证的领域，例如数学和代码。此外，这种方法会引入额外的复杂性和依赖，并可能将部分评估负担从模型本身转移到外部工具上。

由于数学求解可以以编程方式生成无限多的变体，且适合分步推理，这一任务已成为评估和开发推理模型的基石。在本章中，我们将按照图 3.3 所示的八个步骤，一步步构建一个数学验证器。

图 3.3  构建和应用数学验证器的分步工作流。我们从预训练 LLM 开始，生成答案，提取并归一化答案，然后将其与标准解进行比对。验证后的答案被评分，这一过程在数据集（MATH-500）上重复进行，以评估模型的整体性能。

3.4 提取最终答案框

Extracting the final answer box

现在模型已加载就绪，我们可以进入有趣的环节：评估模型。

值得重申的是，本书采用从零开始（from scratch）的方式，这自然会包含一些详细且有时略显繁琐的步骤。这是有意为之。我们希望自己构建评估流水线，以便更深入地理解其工作原理，而不是仅仅调用预定义的封装函数和构建块。

在前一节中，你看到模型将最终答案以答案框的形式返回（原始文本中写为 r"\boxed{\dfrac{14}{3}}"）。我们并未强制要求这种格式；模型之所以产生这种输出，很可能是因为盒式答案是数学基准和训练数据中的常见约定。这种行为不一定证明模型对后续评估任务过拟合，但它反映出预训练模型经常在网上遇到各种问题格式，并学会了复现这些风格惯例。一般来说，可以合理地假设，模型训练时互联网上可获得的任何信息都属于训练数据的组成部分。

虽然此处并非必要，但当我们之后在 MATH-500 数据集上评估模型时，我们会添加一个特定的提示，指示模型以这种盒式形式返回答案。（MATH-500 是一个精心整理的包含 500 个问题的数据集，被广泛用作推理模型的基准数据集。）这一步骤比较直接，并且在我们需要将模型回答转化为可大规模自动评分的形式时，它将反复出现。这种通用约定使跨模型的评估更加一致，并简化了数据提取过程。

为什么不用 LLM 来提取答案？

我们本可以使用 LLM 来提取盒式答案本身，但这会引入不必要的复杂性和潜在错误。假设 LLM 以特定格式输出答案，提取就是一个简单的机械任务：我们只需要定位最后一个盒式表达式，如果缺失则退回到数字或原始文本。

正则表达式乍看起来可能很复杂，但我们现在拥有一个轻量、可复用的工具函数，它执行成本低廉，且能确定性和可重复地处理提取，而不依赖于另一个模型输出的变异性。

3.5 归一化提取出的答案

Normalizing the extracted answer

之前，我们从模型回答中提取了盒式答案 "\dfrac{14}{3}"。模型可能会以多种方式打印相同的数值，例如 "\frac{14}{3}"、"14/3"、"$14/3$" 或 "(14)/(3)"。为了实现并使用一个健壮的检查系统来判断答案是否正确，我们首先需要一种一致的结果比较方法。在本节中，我们将实现一个归一化（或称规范化）过程（图 3.7 中的步骤 4），用于去除格式并标准化答案。

代码清单 3.6  归一化提取出的答案

这个 normalize_text 函数接收提取出的答案字符串，并将其重写为标准化格式，以便我们可以可靠地将其与参考解进行比较。它首先去除特殊 token 和不必要的 LaTeX 杂乱内容，例如 \left、\right 或角度符号。然后它会展开 \text{...} 等情况，移除行内数学标记，并将常用结构重写为计算器风格的格式。例如，它将 \sqrt{a} 转换为 sqrt(a)，将 \frac{a}{b} 转换为 (a)/(b)。最后，它归一化指数、带分数和千位分隔符，并清理花括号和大小写。简而言之，该函数将不同格式的 LaTeX 输出转换为干净、标准化的字符串表示形式。

3.6 验证数学等价性

Verifying mathematical equivalence

到目前为止，我们已经实现了让 LLM 生成答案、提取相关部分并归一化答案的步骤。下一步（如图 3.8 所示）是验证提取出的答案，将其与正确的参考答案（技术上下文中称为标准答案，ground truth）进行比较。我们将在第 6 章再次使用这样的验证器来创建可验证的奖励信号，并在后续章节中使用它来检查我们的训练改进是否真正优化了模型。

注意，在实现图 3.8 所示的相等性检查时，直接使用 Python 的 == 运算符是不够的，因为像 "14/3" 和 "(14)/(3)" 这样的表达式无法匹配，而等价的未归一化分数如 "(28)/(6)" 和 "(14)/(3)" 也会被视为不相等。

作为相等性检查的一部分，我们将增加一个中间步骤：使用符号数学引擎来解析提取并归一化后的答案。为此，我们将使用开源 SymPy 数学库（https://sympy.org），该库经过二十多年的开发和测试，已成为 Python 科学计算的中流砥柱。解析函数在代码清单 3.7 中实现。

注意  如果你尚未安装第 2 章的依赖项，可以手动安装 SymPy：uv pip install sympy（或 uv add sympy）。

图 3.8  将 LLM 生成的答案与正确的参考答案（标准答案）进行比对的示意图。LLM 的最终盒式答案被提取、归一化，然后与数据集中提供的正确答案进行比较。如果匹配，则该回答被评分为正确。

前面我提到过，答案提取是一个简单的机械性任务，可以用确定性代码解决，而不需要借助另一个 LLM 进行答案提取。根据不同提示模板下准确率的变化来看，我们的提取方法可能并不可靠。但事实未必如此。同时，LLM 生成格式不正确的答案也未必是原因——它可能只是答案本身不正确，改用另一个 LLM 进行提取也无法解决这个问题。较小的基础模型通常对提示措辞非常敏感。在下一章中，你会看到一旦我们引入更多的提示变体，这一点会更加明显。

本章小结

  • LLM 主要有四种评估方法：多项选择、验证器、排行榜和 LLM 作为评判者。

  • 基于验证的评估方法允许自由形式的答案，并使用外部工具检查正确性。

  • 本章专注于基于验证的评估，通过构建一个数学验证器，使用 SymPy 提取、标准化和检查答案。

    • 验证流程包括几个核心步骤，从加载 LLM 到在数据集上运行评估。

    • 作为验证流程的一部分，答案提取使用字符串解析来定位框式内容（带有缺失框的备用机制）。

    • 另一个步骤实现了标准化，通过去除 LaTeX 和转换数学符号来统一多样化的答案格式。

  • 最后，流程使用数学等价性检查（通过 SymPy）在符号层面上比较表达式。

  • MATH-500 数据集提供了 500 道精选数学问题用于评估。

  • 提示模板显著影响模型性能。

  • 推理模型比基础模型实现了更高的准确率，但需要更长的运行时间。
