第9章 推理优化

Chapter 9. Inference Optimization

新模型层出不穷，但有一件事始终重要：让它们变得更好、更便宜、更快。到目前为止，本书已经讨论了各种让模型变得更好的技术。本章将聚焦于让模型变得更快、更便宜。无论你的模型有多好，如果它太慢，用户可能会失去耐心，更糟糕的是，其预测结果可能会变得毫无用处——想象一个隔夜股票价格预测模型需要两天时间计算每个结果。如果模型太贵，其投资回报率将得不偿失。

推理优化可以在模型、硬件和服务三个层面进行。在模型层面，你可以减小已训练模型的尺寸，或开发更高效的架构，例如消除Transformer模型中注意力机制的计算瓶颈。在硬件层面，你可以设计更强大的硬件。

推理服务在特定硬件上运行模型以处理用户请求。它可以结合针对特定硬件优化模型的技术，还需要考虑使用模式和流量模式，以高效分配资源，降低延迟和成本。

正因如此，推理优化是一个跨学科领域，通常需要模型研究人员、应用开发者、系统工程师、编译器设计者、硬件架构师甚至数据中心运营者之间的协作。

本章讨论AI推理的瓶颈以及克服这些瓶颈的技术。它主要关注模型和服务层面的优化，并概述AI加速器。

  1. 如第7章所述，推理只涉及前向传播，而训练同时涉及前向和反向传播。
  2. 我的朋友Mark Saroufim向我指出了模型训练成本和推理成本之间的一个有趣关系。假设你是模型提供商。令T为总训练成本，p为每次推理的收费，N为可售出的推理调用次数。开发一个模型只有在从推理中回收的资金超过其训练成本时才划算，即T ≤ p × N。一个模型在生产中使用得越多，模型提供商就越能降低推理成本。然而，这不适用于在开源模型之上销售推理调用的第三方API提供商。

本章还涵盖了性能指标和权衡。有时，加速模型的技术也能降低成本。例如，降低模型精度使其更小、更快。但优化通常需要权衡。例如，最好的硬件可能让模型运行更快，但成本更高。

随着开源模型越来越丰富，越来越多的团队在构建自己的推理服务。然而，即使你不实现这些推理优化技术，理解这些技术也能帮助你评估推理服务和框架。如果你的应用延迟和成本让你困扰，请继续往下读。本章或许能帮你诊断原因并找到潜在解决方案。

理解推理优化

Understanding Inference Optimization

AI模型的生命周期有两个不同的阶段：训练和推理。训练是指构建模型的过程。推理是指使用模型根据给定输入计算输出的过程。¹ 除非你训练或微调模型，否则你主要需要关注推理。²

本节首先概述推理，引入共享词汇以便讨论本章其余内容。如果你已熟悉这些概念，可以跳过感兴趣的部分。

推理概述

Inference Overview

在生产环境中，运行模型推理的组件称为推理服务器。它托管可用的模型并访问必要的硬件。基于来自应用（例如用户提示）的请求，它分配资源以执行相应模型，并将结果返回给用户。推理服务器是更广泛的推理服务的一部分，该服务还负责在请求到达推理服务器之前接收、路由以及可能的预处理请求。一个简单推理服务的可视化如图9-1所示。

计算瓶颈

优化就是识别瓶颈并加以解决。例如，为优化交通，城市规划者可能会识别拥堵点并采取措施缓解拥堵。类似地，推理服务器应设计用于解决其服务推理工作负载的计算瓶颈。主要存在两种计算瓶颈：计算密集型和内存带宽密集型：

计算密集型（Compute-bound） 指任务的完成时间由任务所需的计算量决定。例如，密码解密通常是计算密集型的，因为破解加密算法需要大量的数学计算。

内存带宽密集型（Memory bandwidth-bound） 这些任务受限于系统内的数据传输速率，例如内存与处理器之间的数据移动速度。例如，如果你将数据存储在CPU内存中，而在GPU上训练模型，你必须将数据从CPU移动到GPU，这可能需要很长时间。这可以简称为带宽密集型。在文献中，内存带宽密集型常被称为内存密集型。

术语歧义：内存密集（Memory-Bound）与带宽密集（Bandwidth-Bound）

有些人使用"内存密集型"（memory-bound）来指代任务的完成时间受内存容量而非内存带宽限制的情况。当你的硬件没有足够的内存来处理任务时就会发生这种情况，例如你的机器没有足够的内存来存储整个互联网。这种内存问题通常表现为工程师们都认识的错误：OOM（内存不足）。³

然而，这种情况通常可以通过将任务拆分成更小的部分来缓解。例如，如果你受限于GPU内存，无法将整个模型放入GPU，你可以将模型拆分到GPU内存和CPU内存中。这种拆分会因CPU和GPU之间数据传输的时间而减慢计算速度。然而，如果数据传输足够快，这就不成问题。因此，内存容量限制实际上更多是关于内存带宽的。

计算密集型和内存带宽密集型的概念由论文"Roofline"（Williams等人，2009）提出。⁴ 从数学上讲，一个操作可以根据其算术强度（每字节内存访问的算术操作次数）分类为计算密集型或内存带宽密集型。像NVIDIA Nsight这样的分析工具会显示屋顶线图（roofline chart），告诉你工作负载是计算密集型还是内存带宽密集型，如图9-2所示。这个图表被称为屋顶线图，因为它形似屋顶。屋顶线图在硬件性能分析中很常见。

图9-2. 屋顶线图可以帮助你可视化一个操作是计算密集型还是内存带宽密集型。该图采用对数刻度。

不同的优化技术旨在缓解不同的瓶颈。例如，计算密集型的工作负载可以通过分布到更多芯片上或利用计算能力更强的芯片（例如更高的FLOP/s数值）来加速。内存带宽密集型的工作负载可以通过利用更高带宽的芯片来加速。

不同的模型架构和工作负载会导致不同的计算瓶颈。例如，像Stable Diffusion这样的图像生成器的推理通常是计算密集型的，而自回归语言模型的推理通常是内存带宽密集型的。

在大语言模型推理中，预填充（Prefilling） 指的是模型处理输入提示（prompt）的阶段。简单说，就是把用户输入的整段文本一次性喂给模型，计算出第一个输出token的过程。

一、为什么叫"预填充"

Transformer 是自回归生成的，每生成一个 token 都需要参考之前所有 token 的 Key/Value（KV）。生成第一个新 token 之前，必须先把 prompt 里所有 token 的 KV 算出来并存入缓存——这个"预先填充 KV 缓存"的动作，就叫 prefilling。

二、预填充 vs 解码 的对比

维度 预填充（Prefilling） 解码（Decoding）
处理对象 整个 prompt（可能几千token） 每次只处理1个新token
并行性 高度并行，所有位置同时算 串行，必须等上一个token生成
计算瓶颈 计算密集（compute-bound） 显存带宽密集（memory-bound）
耗时占比 通常较短（并行快） 随生成长度线性增长
产出 第一个输出token + KV缓存 后续每个token

四、关键点

  1. 预填充只做一次，处理整个prompt；解码做N次（N=生成长度）。

  2. KV Cache 是核心。预填充把 prompt 的 KV 全部算好缓存，解码时就不需要重算历史token，大幅提速。

  3. 预填充是计算瓶颈，解码是显存瓶颈：

    • 预填充：矩阵大、并行度高，GPU算力吃满。
    • 解码：每步只算一个token，但要读取整个KV Cache，受显存带宽限制。

  4. 首token延迟（TTFT, Time To First Token） 主要由预填充时间决定；每token延迟（TPOT） 由解码决定。

五、实际影响

  • Prompt 越长，预填充越慢（但仍是并行的，比逐token快得多）。
  • 这就是为什么"长上下文"模型要优化注意力机制（如 FlashAttention、稀疏注意力）——主要为了加速预填充。
  • 也是为什么连续批处理（continuous batching）等技术要区分 prefilling 和 decoding 两个阶段来调度。

一句话总结

预填充 = 把整个输入prompt并行过一遍模型，算出第一个输出token并建立KV缓存；之后的解码阶段则逐个token串行生成，复用KV缓存避免重复计算。

预填充（Prefill） 模型并行处理输入token。⁵ 一次能处理多少token受限于硬件在给定时间内能执行的操作数量。因此，预填充是计算密集型的。

解码（Decode） 模型一次生成一个输出token。在高层面上，这一步骤通常涉及将大型矩阵（如模型权重）加载到GPU中，这受限于硬件将数据加载到内存的速度。因此，解码是内存带宽密集型的。

截至撰写本文时，由于Transformer架构的普及和现有加速器技术的局限性，许多AI和数据工作负载仍是内存带宽密集型的。然而，未来的软件和硬件进步将使AI和数据工作负载变为计算密集型。

在线推理API和批量推理API

许多提供商提供两种类型的推理API：在线和批量：

  • 在线API优化延迟。请求一旦到达即被处理。
  • 批量API优化成本。如果您的应用没有严格的延迟要求，可以将其发送到批量API进行更高效的处理。更高的延迟允许更广泛的优化技术，包括将请求批量聚合以及使用更便宜的硬件。例如，截至撰写本文时，Google Gemini和OpenAI都提供批量API，成本降低50%，但周转时间显著增加，即数小时而不是数秒或数分钟。⁶

在线API仍可能将请求批量聚合，只要不会显著影响延迟，这一点将在"批处理"一节中讨论。唯一的真正区别在于，在线API注重更低的延迟，而批量API更注重更高的吞吐量。

面向客户的使用场景，如聊天机器人和代码生成，通常需要较低的延迟，因此倾向于使用在线API。延迟要求不那么严格的使用场景（适合批量API）包括：

  • 合成数据生成
  • 定期报告，如总结Slack消息、分析社交媒体上的品牌提及情感、分析客户支持工单
  • 需要处理所有已上传文档的新客户入职
  • 迁移到需要重新处理所有数据的新模型
  • 为大量客户群生成个性化推荐或新闻通讯
  • 通过重新索引组织数据来更新知识库

API通常默认返回完整响应。然而，对于自回归解码，模型完成响应可能需要很长时间，而用户缺乏耐心。许多在线API提供流式模式，即在生成每个token时立即返回。这减少了用户等待第一个token的时间。这种方法的缺点是你无法在向用户展示响应之前对其进行评分，增加了用户看到不良响应的风险。不过，一旦检测到风险，你仍然可以事后更新或删除响应。

基础模型的批量API与传统ML的批量推理不同。在传统ML中： * 在线推理意味着在请求到达后计算预测结果。 * 批量推理意味着在请求到达前预先计算预测结果。

对于输入有限且可预测的使用场景（如推荐系统，可以预先为所有用户生成推荐），预计算是可行的。当请求到达时（例如用户访问网站），直接获取这些预计算的预测结果。然而，对于基础模型的使用场景，输入是开放式的，很难预测所有用户的提示。⁷

推理性能指标

Inference Performance Metrics

在深入优化之前，了解要优化哪些指标非常重要。从用户角度来看，核心指标是延迟（响应质量是模型本身的属性，而非推理服务的属性）。然而，应用开发者还必须考虑吞吐量和利用率，因为它们决定了应用的成本。

延迟、TTFT和TPOT

延迟衡量从用户发送查询到收到完整响应的时间。对于自回归生成，尤其是在流式模式下，总体延迟可以分解为多个指标：

首token时间（Time to First Token, TTFT） TTFT衡量用户发送查询后生成第一个token的速度。它对应于预填充步骤的持续时间，取决于输入的长度。不同应用的用户对TTFT可能有不同的期望。例如，对于对话式聊天机器人，TTFT应该是即时的。⁸ 然而，用户可能愿意等待更长时间来总结长文档。

每个输出token时间（Time Per Output Token, TPOT） TPOT衡量在第一个token之后生成每个输出token的速度。如果每个token需要100毫秒，那么1000个token的响应将需要100秒。

在流式模式下，用户逐字阅读生成的token，TPOT应快于人类的阅读速度，但不必快太多。一个非常快的阅读者可以阅读120毫秒/token，因此约120毫秒的TPOT（即6-8 tokens/秒）对大多数使用场景来说足够了。

token间隔时间（Time Between Tokens）和token间延迟（Inter-Token Latency） 此指标的变体包括token间隔时间（TBT）和token间延迟（ITL）。⁹ 两者都衡量输出token之间的时间。

总延迟等于TTFT + TPOT ×（输出token数量）。

两个总延迟相同的应用，其TTFT和TPOT不同，可能带来不同的用户体验。你的用户是希望第一时间看到第一个token但后续token等待较长，还是愿意稍微多等一会儿第一个token但享受更快的后续生成？需要通过用户研究来确定最佳用户体验。通过将更多计算实例从解码转移到预填充或反之，可以在牺牲更高TPOT的情况下降低TTFT。¹⁰

需要注意的是，用户观察到的TTFT和TPOT值可能与模型内部的值不同，特别是在涉及思维链（CoT）或智能体查询的场景中，模型生成的中间步骤不会展示给用户。一些团队使用"发布到用户时间"（time to publish）这个指标来明确表示它衡量的是用户看到的第一个token的时间。

考虑以下场景：用户发送查询后，模型执行以下步骤：

  1. 生成一个计划，包含一系列操作。这个计划不显示给用户。
  2. 执行操作并记录其输出。这些输出不显示给用户。
  3. 基于这些输出，生成最终响应展示给用户。

从模型的角度看，第一个token在第1步就生成了。这是模型内部开始其token生成过程的时间。然而，用户只看到第3步生成的最终输出的第一个token。因此，从用户角度看，TTFT要长得多。

由于延迟是一个分布，平均值可能具有误导性。假设有10个请求，其TTFT值分别为100 ms、102 ms、100 ms、100 ms、99 ms、104 ms、110 ms、90 ms、3000 ms、95 ms。平均TTFT值为390 ms，这使你的推理服务看起来比实际更慢。可能是网络错误减慢了一个请求的速度，或者一个特别长的提示需要更长时间来预填充。无论哪种情况，你都应该进行调查。在大量请求的情况下，扭曲平均延迟的异常值几乎不可避免。

查看延迟的百分位数更有帮助，因为它们能告诉你关于一定比例请求的信息。最常见的百分位数是第50百分位数，缩写为p50（中位数）。如果中位数是100 ms，则一半的请求生成第一个token的时间超过100 ms，一半少于100 ms。百分位数还能帮助你发现异常值，这些异常值可能是某些问题的症状。通常，你应该关注的百分位数是p90、p95和p99。将TTFT值与输入长度绘制成图表也很有帮助。

吞吐量和有效吞吐量（Goodput）

吞吐量衡量推理服务在所有用户和请求中每秒能生成的输出token数量。

一些团队在计算吞吐量时同时计算输入和输出token。然而，由于处理输入token（预填充）和生成输出token（解码）具有不同的计算瓶颈，并且在现代推理服务器中通常被解耦，因此输入和输出吞吐量应分别计算。当吞吐量不加修饰语使用时，通常指的是输出token。

吞吐量通常以tokens/s（TPS）衡量。如果你服务多个用户，tokens/s/user也用于评估系统随用户增加时的扩展能力。

吞吐量也可以衡量为在给定时间内完成的请求数量。许多应用使用每秒请求数（RPS）。然而，对于基于基础模型构建的应用，一个请求可能需要数秒才能完成，因此许多人使用每分钟完成请求数（RPM）。跟踪这一指标有助于了解推理服务器如何处理并发请求。如果你同时发送太多并发请求，一些提供商可能会限制你的服务。

吞吐量与计算成本直接相关。更高的吞吐量通常意味着更低的成本。如果你的系统计算成本为$2/小时，吞吐量为100 tokens/s，那么每1M输出token的成本约为$5.556。如果每个请求平均生成200个输出token，解码1K个请求的成本为$1.11。

预填充成本可以类似计算。如果你的硬件成本为$2/小时，每分钟可以预填充100个请求，那么预填充1K个请求的成本为$0.33。

每个请求的总成本是预填充成本和解码成本之和。在这个例子中，1K个请求的总成本为$1.11 + $0.33 = $1.44。

什么被认为是好的吞吐量取决于模型、硬件和工作负载。较小的模型和较高端的芯片通常产生更高的吞吐量。输入和输出长度一致的工作负载比长度变化的工作负载更容易优化。

即使对于相似规模的模型、硬件和工作负载，直接比较吞吐量可能也只是近似值，因为token数量取决于什么构成一个token，且不同模型有不同的分词器。使用每个请求的成本等指标来比较推理服务器的效率更好。

与大多数其他软件应用一样，AI应用也存在延迟/吞吐量的权衡。像批处理这样的技术可以提高吞吐量，但会降低延迟。根据LinkedIn AI团队在部署生成式AI产品一年后的反思（LinkedIn，2024年），如果你愿意牺牲TTFT和TPOT，吞吐量翻倍或三倍的情况并不少见。

由于这种权衡，仅根据吞吐量和成本来评估推理服务可能导致糟糕的用户体验。因此，一些团队关注有效吞吐量（goodput），这是一个从网络领域借鉴用于LLM应用的指标。有效吞吐量衡量每秒满足SLO（服务水平目标）的请求数量。

假设你的应用有以下目标：TTFT不超过200 ms，TPOT不超过100 ms。假设你的推理服务每分钟可以完成100个请求。然而，在这100个请求中，只有30个满足SLO。那么，该服务的有效吞吐量为30个请求/分钟。图9-4展示了这一情况。

利用率、MFU和MBU

利用率指标衡量资源被使用的效率。它通常量化资源被积极使用的比例与其总可用容量之比。

一个常见但常被误解的指标是GPU利用率，NVIDIA对此负有一定责任。官方的NVIDIA GPU使用监控工具是nvidia-smi——SMI代表系统管理接口（System Management Interface）。该工具显示的一个指标是GPU利用率，表示GPU积极处理任务的时间百分比。例如，如果你在GPU集群上运行推理10小时，其中GPU积极处理任务5小时，那么你的GPU利用率为50%。

然而，积极处理任务并不意味着高效处理。为简单起见，考虑一个微小的GPU，每秒能执行100次操作。根据nvidia-smi对利用率的定义，即使该GPU每秒只做一次操作，它也可能报告100%的利用率。

如果你为一台能做100次操作的机器付费，却只使用它做1次操作，你就是在浪费钱。因此，nvidia-smi的GPU优化指标并不是很有用。你可能关心的利用率指标是：在一台机器能够计算的所有操作中，它在给定时间内实际完成了多少。这个指标称为MFU（Model FLOP/s Utilization），以区别于NVIDIA的GPU利用率指标。¹¹

MFU是观察到的吞吐量（tokens/s）与系统在峰值FLOP/s下运行时的理论最大吞吐量之比。如果芯片在芯片制造商宣传的峰值FLOP/s下每秒可以生成100个token，但在你的推理服务中每秒只能生成20个token，那么你的MFU就是20%。¹²

类似地，由于内存带宽昂贵，你可能还想知道硬件的带宽利用效率如何。MBU（Model Bandwidth Utilization）衡量可达到的内存带宽的使用百分比。如果芯片的峰值带宽为1 TB/s，而你的推理仅使用了500 GB/s，那么你的MBU为50%。

Q： 究竟是内存贵还是内存带宽贵？

A：

这两个说法其实不矛盾，但“贵”指的对象不同，容易混淆。拆开看：

一、先区分两个概念

概念 含义 衡量单位
内存容量 能存多少数据（显存多大） GB
内存带宽 数据读写的速度（每秒能搬多少） GB/s

“内存贵” 通常指 容量 贵——买 80GB 显存的 H100 比 40GB 的贵很多。

“内存带宽昂贵” 指的是 带宽资源稀缺、是性能瓶颈——不是价格贵，而是“不够用、很宝贵”。

二、为什么说“内存带宽昂贵”

在 LLM 解码阶段，瓶颈往往不是算力，而是显存带宽：

举个例子： - A100 算力约 312 TFLOPS（FP16） - A100 显存带宽约 2 TB/s

做矩阵向量乘时，算力严重过剩，带宽成为天花板。这时候我们说“内存带宽是稀缺资源 / 昂贵”——指的是它是限制性能的关键瓶颈，用一点少一点，不是说它价格高。

三、所以到底哪个“贵”

要看你说的“贵”是哪个意思：

说法 实际含义 对吗
内存（容量）贵 显存容量成本高，加显存很花钱 ✅ 对
内存带宽贵 带宽是性能瓶颈，稀缺、宝贵 ✅ 也对，但指“瓶颈”不是“价格”
内存带宽比容量贵 单位成本上带宽更贵 视场景，通常带宽确实更难堆

关键：HBM（高带宽显存）之所以贵，正是因为既要大容量又要高带宽，而高带宽的物理实现（堆叠、宽总线）成本极高。所以严格说，HBM 是“容量和带宽都贵”，而带宽往往是更难提升、更卡脖子的那个。

四、一句话总结

“内存贵”多指容量成本高；“内存带宽昂贵”指的是带宽是性能瓶颈、资源稀缺。两者不冲突——HBM 恰恰是容量和带宽都贵，而在 LLM 解码这种 memory-bound 场景里，带宽是那个真正卡住速度的稀缺资源。

如果你看到的那段话是在讲 LLM 推理优化（比如为什么用 KV Cache 量化、GQA、FlashAttention），那它说的“昂贵”基本就是带宽瓶颈这个意思。

一句话总结

GPU 确实直接读写显存，但运算必须先把数据从显存搬进计算单元。这个“显存→寄存器”的搬运速度就是显存带宽——解码时每 token 都要搬全部权重，算力远快于搬运，于是带宽成了瓶颈，计算单元在等数据。这就是“内存带宽昂贵”的真正含义。

计算LLM推理所使用的内存带宽很简单：

​ 参数数量 × 字节/参数 × tokens/s

MBU的计算如下：

​ (参数数量 × 字节/参数 × tokens/s) / (理论带宽)

例如，如果你使用一个7B参数的FP16模型（每个参数2字节），达到100 tokens/s，则使用的带宽为：

​ 7B × 2 × 100 = 700 GB/s

这突显了量化（在第7章讨论）的重要性。每个参数的字节数越少，模型消耗的宝贵带宽就越少。

如果这是在A100-80GB GPU上完成的，其理论内存带宽为2 TB/s，则MBU为：

​ (700 GB/s) / (2 TB/s) = 70%

吞吐量（tokens/s）与MBU之间以及吞吐量与MFU之间是线性关系，因此有些人可能用吞吐量来指代MBU和MFU。

什么被认为是好的MFU和MBU取决于模型、硬件和工作负载。计算密集型工作负载通常具有较高的MFU和较低的MBU，而带宽密集型工作负载通常显示出较低的MFU和较高的MBU。

由于训练可以从更高效的优化（例如更好的批处理）中受益，且工作负载更可预测，训练的MFU通常高于推理的MFU。对于推理，由于预填充是计算密集型的而解码是内存带宽密集型的，预填充期间的MFU通常高于解码期间的MFU。对于模型训练，截至撰写本文时，MFU超过50%通常被认为是好的，但在特定硬件上可能很难实现。¹³ 表9-1展示了几种模型和加速器的MFU。

AI加速器

AI Accelerators

软件运行的速度和成本取决于它运行在什么硬件上。虽然存在跨硬件通用的优化技术，但了解硬件可以实现更深层次的优化。本节从推理角度审视硬件，但其内容也适用于训练。

AI模型与硬件的发展始终交织在一起。缺乏足够强大的计算机是1970年代第一次AI寒冬的促成因素之一。¹⁴

2012年深度学习兴趣的复兴也与计算能力密切相关。AlexNet（Krizhevsky等人，2012）之所以流行的一个公认原因是它是第一篇成功使用GPU（图形处理单元）训练神经网络的论文。¹⁵ 在GPU之前，如果你想要训练AlexNet规模的模型，必须使用数千个CPU，就像Google在AlexNet前几个月发布的那样。相比于数千个CPU，几个GPU对于博士生和研究人员来说更容易获得，从而引发了深度学习研究的热潮。

什么是加速器?

加速器是一种为加速特定类型计算工作负载而设计的芯片。AI加速器是为AI工作负载设计的。主流的AI加速器类型是GPU，而2020年代初期AI热潮中最大的经济驱动力无疑是NVIDIA。

CPU和GPU的主要区别在于，CPU是为通用用途设计的，而GPU是为并行处理设计的：

  • CPU拥有少数强大的核心，高端消费级机器通常最多64个核心。虽然许多CPU核心可以有效处理多线程工作负载，但它们擅长的是需要高单线程性能的任务，如运行操作系统、管理I/O（输入/输出）操作或处理复杂的顺序进程。
  • GPU拥有数千个较小、功能较弱的核心，针对可以分解为许多更小、独立计算的任务进行了优化，如图形渲染和机器学习。构成大多数ML工作负载的操作是矩阵乘法，它具有高度可并行性。¹⁶

虽然追求高效并行处理提高了计算能力，但也给内存设计和功耗带来了挑战。

NVIDIA GPU的成功激发了众多为加速AI工作负载而设计的加速器，包括Advanced Micro Devices (AMD)的新一代GPU、Google的TPU（张量处理单元）、Intel的Habana Gaudi、Graphcore的智能处理单元（IPU）、Groq的语言处理单元（LPU）、Cerebras的晶圆级量子处理单元（QPU）以及更多正在推出的产品。

虽然许多芯片可以同时处理训练和推理，但一个正在兴起的大趋势是专门用于推理的芯片。Desislavov等人（2023）的一项调查指出，在常用系统中，推理成本可能超过训练成本，推理在已部署的AI系统中占机器学习成本的90%。

如第7章所述，训练由于反向传播需要更多的内存，并且通常在较低精度下更难执行。此外，训练通常强调吞吐量，而推理旨在最小化延迟。因此，专为推理设计的芯片通常针对更低精度和更快的内存访问进行优化，而不是大的内存容量。此类芯片的例子包括Apple Neural Engine、AWS Inferentia和MTIA（Meta训练和推理加速器）。为边缘计算设计的芯片，如Google的Edge TPU和NVIDIA Jetson Xavier，也通常面向推理。

还有针对不同模型架构的专用芯片，例如专为Transformer设计的芯片。¹⁷ 许多芯片是为数据中心设计的，越来越多的芯片正在为消费设备（如手机和笔记本电脑）设计。

计算能力

计算能力通常以芯片在给定时间内能执行的操作数量来衡量。最常见的指标是FLOP/s（常写作FLOPS），衡量每秒的峰值浮点运算次数。然而，实际上应用极难达到这个峰值FLOP/s。实际FLOP/s与理论FLOP/s的比率就是利用率指标之一。

芯片每秒能执行的操作数量取决于数值精度——精度越高，芯片能执行的操作越少。可以这么理解：将两个32位数字相加通常需要两倍于两个16位数字相加的计算量。由于不同芯片的优化不同，芯片在给定时间内能执行的32位操作数量并不恰好是16位操作的一半。有关数值精度概览，请回顾第7章"数值表示"部分。

内存大小和带宽

由于GPU有许多核心并行工作，数据通常需要从内存移动到这些核心，因此数据传输速度非常重要。在处理涉及大型权重矩阵和训练数据的AI模型时，数据传输至关重要。这些大量数据需要快速移动以保持核心高效运转。因此，GPU内存需要比CPU内存更高的带宽和更低的延迟，这使得GPU内存需要更先进的内存技术。这是GPU内存比CPU内存更昂贵的原因之一。

更具体地说，CPU通常使用DDR SDRAM（双倍数据率同步动态随机存取存储器），具有二维结构。GPU，尤其是高端GPU，通常使用HBM（高带宽内存），具有三维堆叠结构。¹⁸

CPU内存（DRAM） 加速器通常与CPU一起部署，因此可以访问CPU内存（也称为系统内存、主机内存或CPU DRAM）。 CPU内存通常是这些内存类型中带宽最低的，数据传输速度在25 GB/s到50 GB/s之间。CPU内存大小各不相同。普通笔记本电脑可能有16-64 GB，而高端工作站可能有一TB或更多。

GPU高带宽内存（HBM） 这是专用于GPU的内存，位于GPU附近，访问速度比CPU内存更快。 HBM提供显著更高的带宽，数据传输速度通常在256 GB/s到1.5 TB/s以上之间。这个速度对于高效处理大数据传输和高吞吐量任务至关重要。消费级GPU拥有约24-80 GB的HBM。

GPU片上SRAM 集成在芯片内部，用于存储频繁访问的数据和指令，实现几乎即时的访问。它包括由SRAM制成的L1和L2缓存，在某些架构中还有L3缓存。这些缓存是更广泛的片上内存的一部分，还包括寄存器文件和共享内存等其他组件。 RAM具有极高的数据传输速度，通常超过10 TB/s。GPU SRAM的大小很小，通常在40 MB或以下。

大量的GPU优化工作都围绕着如何充分利用这个内存层次结构。然而，截至撰写本文时，像PyTorch和TensorFlow这样的流行框架还不允许对内存访问进行细粒度控制。这导致许多AI研究人员和工程师对GPU编程语言产生了兴趣，如CUDA（最初代表统一计算设备架构）、OpenAI的Triton和ROCm（Radeon开放计算平台）。后者是AMD对NVIDIA专有CUDA的开源替代方案。

功耗

芯片依靠晶体管进行计算。每次计算都需要晶体管开关，这需要能量。GPU拥有数十亿个晶体管——NVIDIA A100有540亿个晶体管，而NVIDIA H100有800亿个。当加速器被高效使用时，数十亿个晶体管快速切换状态，消耗大量能量并产生大量热量。这些热量需要冷却系统，这也消耗电力，增加了数据中心的总能耗。

芯片的能耗可能对环境产生惊人影响，加大了公司投资绿色数据中心技术的压力。一块NVIDIA H100满负荷运行一年大约消耗7,000 kWh。作为对比，美国家庭年均用电量为10,000 kWh。这就是为什么电力是扩展计算的瓶颈。¹⁹

加速器通常以最大功率消耗或代理指标TDP（热设计功耗）来指定功耗：

  • 最大功率消耗表示芯片在满载时可能消耗的峰值功率。
  • TDP表示芯片在典型工作负载下运行时，冷却系统需要散发的最大热量。虽然它不是功耗的精确度量，但它是预期功率消耗的指标。对于CPU和GPU，最大功率消耗大约为TDP的1.1到1.5倍，但具体关系因架构和工作负载而异。

如果你选择使用云服务提供商，则无需担心冷却或电力问题。然而，这些数字对于理解加速器对环境的影响和总体电力需求仍然有参考价值。

选择加速器

使用什么加速器取决于你的工作负载。如果你的工作负载是计算密集型的，你可能需要寻找具有更高FLOP/s的芯片。如果你的工作负载是内存密集型的，购买更高带宽和更大内存的芯片会让你的生活更轻松。

在评估购买哪种芯片时，主要有三个问题：

  • 硬件能否运行你的工作负载？
  • 运行需要多长时间？
  • 成本是多少？

FLOP/s、内存大小和内存带宽是帮助你回答前两个问题的三个重要数字。最后一个问题很直接。云提供商的定价通常基于使用量，并且各提供商之间相当相似。如果你购买自己的硬件，成本可以根据初始价格和持续的功耗来计算。

模型优化

Model Optimization

模型级优化旨在使模型更高效，通常通过修改模型本身来实现，这可能会改变其行为。截至撰写本文时，许多基础模型采用Transformer架构，并包含自回归语言模型组件。这些模型有三个使推理资源密集的特性：模型大小、自回归解码和注意力机制。让我们讨论解决这些挑战的方法。

模型压缩

模型压缩涉及减小模型尺寸的技术。使模型更小也可以使其更快。本书已经讨论了两种模型压缩技术：量化和蒸馏。量化——降低模型精度以减小内存占用并提高吞吐量——在第7章中讨论。模型蒸馏——训练一个小型模型来模仿大型模型的行为——在第8章中讨论。

模型蒸馏表明，使用更少的参数捕捉大型模型的行为是可能的。那么在大型模型内部，是否存在能够捕捉整个模型行为的参数子集？这是剪枝（pruning）的核心概念。

剪枝在神经网络语境中有两种含义。一种是移除神经网络的整个节点，这意味着改变其架构并减少其参数数量。另一种是找到对预测最无用的参数并将其设为零。在这种情况下，剪枝不会减少总参数数量，只减少非零参数的数量。这使得模型更加稀疏，既减少了模型的存储空间，也加快了计算速度。

剪枝后的模型可以原样使用，或进一步微调以调整剩余参数，恢复剪枝过程引起的任何性能退化。剪枝有助于发现有前景的模型架构（Liu等人，2018）。这些剪枝后的架构比剪枝前的架构小，也可以从头开始训练（Zhu等人，2017）。

文献中有许多令人鼓舞的剪枝结果。例如，Frankle和Carbin（2019）表明，剪枝技术可以将某些训练网络的非零参数数量减少超过90%，在降低内存占用和提高速度的同时不影响准确率。然而，在实践中，截至撰写本文时，剪枝并不常见。它更难实施，因为它需要理解原始模型的架构，而且其带来的性能提升通常远不如其他方法。剪枝还会产生稀疏模型，并非所有硬件架构都设计为利用这种稀疏性。

仅权重量化（weight-only quantization）是迄今为止最流行的方法，因为它易于使用，对许多模型开箱即用，且极为有效。将模型精度从32位降低到16位可将其内存占用减半。然而，我们已接近量化的极限——每个值不能低于1比特。蒸馏也很常见，因为它可以产生一个较小的模型，其行为对于你的需求来说可与更大的模型媲美。

克服自回归解码瓶颈

如第2章所述，自回归语言模型一个一个地生成token。如果生成一个token需要100毫秒，那么100个token的响应将需要10秒。¹⁹ 这个过程不仅慢，而且昂贵。在模型API提供商中，一个输出token的价格大约是输入token的两到四倍。在一项实验中，Anyscale发现单个输出token对延迟的影响可能与100个输入token相同（Kadous等人，2023）。哪怕改进自回归生成过程几个百分点，也能显著改善用户体验。

由于该领域发展迅速，新技术不断涌现以克服这个似乎不可逾越的瓶颈。也许有一天会出现没有这个瓶颈的架构。这里涵盖的技术旨在展示解决方案可能的样子，但这些技术仍在演进中。

推测性解码（Speculative decoding）。 推测性解码（也称为推测性采样）使用一个更快但能力较弱的模型生成一串token，然后由目标模型进行验证。目标模型是你想要使用的模型。这个更快的模型称为草稿模型（draft model）或提议模型（proposal model），因为它提出草稿输出。

假设输入token为x₁, x₂, …, xₜ：

  1. 草稿模型生成K个token的序列：xₜ₊₁, xₜ₊₂, …, xₜ₊ₖ。
  2. 目标模型并行验证这K个生成的token。
  3. 目标模型从左到右接受草稿token中最长的子序列，即目标模型同意使用的部分。
  4. 假设目标模型接受了j个草稿token：xₜ₊₁, xₜ₊₂, …, xₜ₊ⱼ。然后目标模型生成一个额外的token：xₜ₊ⱼ₊₁。

该过程返回步骤1，草稿模型基于x₁, x₂, …, xₜ, xₜ₊₁, xₜ₊₂, …, xₜ₊ⱼ生成K个token。整个过程如图9-9所示。

如果没有草稿token被接受，这个循环只产生目标模型生成的一个token。如果所有草稿token都被接受，这个循环产生K+1个token，其中K个由草稿模型生成，1个由目标模型生成。

如果所有草稿序列都被拒绝，目标模型除了验证之外还必须生成整个响应，可能导致延迟增加。然而，由于以下三个洞察，这种情况可以避免：

  1. 目标模型验证一串token所需的时间少于生成它的时间，因为验证是可并行的，而生成是顺序的。推测性解码有效地将解码的计算特征转变为预填充的特征。
  2. 在输出token序列中，有些token比其他token更容易预测。有可能找到一个较弱的草稿模型，能够正确预测这些较容易预测的token，从而实现草稿token的高接受率。
  3. 解码是内存带宽密集型的，这意味着在解码过程中通常存在空闲的FLOPs，可以免费用于验证。²⁰

接受率依赖于领域。对于遵循特定结构的文本，如代码，接受率通常更高。更大的K值意味着目标模型的验证调用次数更少，但草稿token的接受率较低。草稿模型可以是任何架构，但理想情况下应与目标模型共享相同的词汇表和分词器。你可以训练自定义草稿模型或使用现有的较弱模型。

例如，为了加速Chinchilla-70B的解码过程，DeepMind训练了一个相同架构的4B参数草稿模型（Chen等人，2023）。草稿模型生成token的速度比目标模型快8倍（1.8毫秒/token对比14.1毫秒/token）。这使得总体响应延迟降低了超过一半，且不影响响应质量。T5-XXL也实现了类似的加速（Laviathan等人，2022）。

这种方法已经获得广泛采用，因为它相对容易实现，且不会改变模型质量。例如，在PyTorch中用50行代码即可实现。它已被整合到流行的推理框架中，如vLLM、TensorRT-LLM和llama.cpp。

参考推理（Inference with reference）。 通常，响应需要引用输入中的token。例如，如果你向模型询问关于附件文档的问题，模型可能会逐字重复文档中的文本段落。另一个例子是，如果你要求模型修复代码中的错误，模型可能会重用大部分原始代码，仅做少量修改。与其让模型生成这些重复的token，不如从输入中复制这些token以加快生成速度？这就是参考推理的核心思想。

个人注： Q： 以上所说的参考推理和缓存命中是不是同一概念？

A：

不是同一个概念。它们的目标虽然都是“加速生成”，但作用机制完全不同。

核心区别

维度 参考推理 (Inference with Reference) 缓存命中 (Cache Hit)
核心思想 跳过生成步骤，直接“复制” 复用计算结果，避免“重算”

参考推理：跳过生成，直接“复制”

参考推理的核心是“抄近路”。它观察到，当模型引用输入文本时（如 RAG 问答或代码修复），其输出往往与输入中的参考文档存在大量完全相同的文本片段。

它的做法是：在解码过程中，如果检测到当前生成的几个 Token 与参考文档中的某个片段匹配，就直接将该片段后续的若干个 Token 作为候选，一次性复制到模型的输入中。然后，模型在一次前向计算中并行验证这些被“复制”的 Token 是否真的合理，如果是，就一次性接受它们，从而在一步内生成多个 Token。这本质上是用“复制+验证”替代了逐字的“生成”。

缓存命中：复用状态，避免“重算”

缓存命中则侧重于“省力”。它针对的是模型在处理具有相同前缀的请求时（如多轮对话或共享长系统提示），无需重复计算前缀部分的 Key-Value 缓存（KV Cache）。

它的做法是：系统将之前处理过的提示前缀的 KV Cache 保存起来。当新请求到来时，如果检测到其前缀与缓存中的某条记录完全一致，就直接加载这份现成的 KV Cache，跳过整个前缀的预填充计算，直接从新内容开始处理。这本质上是用“读取缓存”替代了“重复计算”。

总结

参考推理是在输出内容层面做文章，通过“复制粘贴”来跳过生成步骤；而缓存命中是在计算过程层面做文章，通过“复用结果”来跳过预填充计算。两者可以同时使用，从不同角度加速推理。

所以：技术上跨用户可命中，工程上常按用户/租户隔离。

参考推理类似于推测性解码，但它不是使用模型生成草稿token，而是从输入中选择草稿token。关键挑战在于开发一种算法，在每步解码时从上下文中识别出最相关的文本片段。最简单的选择是找到与当前token匹配的文本片段。

与推测性解码不同，参考推理不需要额外的模型。然而，它只在上下文与输出之间存在显著重叠的生成场景中才有用，例如检索系统、编码或多轮对话。在"推理参考：大型语言模型的无损加速"（Yang等人，2023）中，该技术在这类使用场景中实现了两倍的生成加速。

并行解码（Parallel decoding）。 一些技术不是通过草稿token来加速自回归生成，而是试图打破顺序依赖性。给定现有的token序列x₁, x₂, …, xₜ，这些技术尝试同时生成xₜ₊₁, xₜ₊₂, …, xₜ₊ₖ。这意味着模型在知道其前一个token是xₜ₊₁之前就生成了xₜ₊₂。

这之所以可行，是因为现有序列的知识通常足以预测后续几个token。例如，给定"the cat sits"，虽然不知道下一个token是"on"、"under"还是"behind"，但你可能仍然能预测再下一个词是"the"。

并行token可以由同一个解码器生成（如Lookahead解码，Fu等人，2024），或由不同的解码头生成（如Medusa，Cai等人，2024）。在Medusa中，原始模型被扩展了多个解码头，每个头是一个小型神经网络层，经过训练来预测特定位置的未来token。如果原始模型被训练来预测下一个token xₜ₊₁，那么第k个头将预测token xₜ₊ₖ₊₁。这些头与原始模型一起训练，但原始模型被冻结。NVIDIA声称Medusa帮助在HGX H200 GPU上将Llama 3.1的token生成速度提升多达1.9倍（Eassa等人，2024）。

  1. K个未来token被并行生成。
  2. 这K个token经过一致性验证，确保与上下文连贯一致。
  3. 如果一个或多个token验证失败，模型不会聚合所有K个未来token，而是仅重新生成或调整这些失败的token。

模型不断精炼生成的token，直到它们全部通过验证并整合到最终输出中。这一类并行解码算法也称为Jacobi解码。

注意力机制优化

回顾第2章，生成下一个token需要所有之前token的键（key）和值（value）向量。这意味着：

  • 生成token xₜ需要token x₁, x₂, …, xₜ₋₁的键和值向量。
  • 生成token xₜ₊₁需要token x₁, x₂, …, xₜ₋₁, xₜ的键和值向量。

当生成token xₜ₊₁时，不需要重新计算token x₁, x₂, …, xₜ₋₁的键和值向量，而是从上一步重用这些向量。这意味着只需要计算最新token xₜ的键和值向量。存储键和值向量以供重用的缓存称为KV缓存。

新计算出的键和值向量随后被添加到KV缓存中，如图9-12所示。

图9-12. 为避免在每步解码时重新计算键和值向量，使用KV缓存来存储这些向量以供重用。

KV缓存仅在推理期间使用，而非训练期间。在训练中，由于序列中的所有token都是预先已知的，下一个token的生成可以一次性计算完成，而非像推理时那样顺序进行。因此，不需要KV缓存。

由于生成一个token需要与所有之前token计算注意力分数，注意力计算的数量随序列长度呈指数增长。²² 而KV缓存大小随序列长度线性增长。KV缓存大小也随更大的批量大小增长。Google的一篇论文计算得出，对于500B+参数的模型（使用多头注意力、批量大小512、上下文长度2048），KV缓存总计3TB（Pope等人，2022）。这相当于该模型权重的三倍。

KV缓存大小最终受限于可用的硬件存储，这成为运行长上下文应用的瓶颈。大的缓存大小也需要时间加载到内存中，对于有严格延迟要求的应用来说可能是个问题。注意力机制的计算和内存需求是难以支持更长上下文的原因之一。

为了提升注意力机制的效率，已经开发了许多技术。总的来说，它们可以分为三类：重新设计注意力机制、优化KV缓存，以及编写注意力计算的内核。

计算KV缓存大小

未经优化的KV缓存所需内存计算如下：

2 × B × S × L × H × M

  • B：批量大小
  • S：序列长度
  • L：Transformer层数
  • H：模型维度
  • M：缓存数值表示所需的内存（例如FP16或FP32）

随着上下文长度增加，这个值可能变得相当大。例如，LLaMA 2 13B有40层，模型维度为5,120。在批量大小为32、序列长度为2,048、每个值2字节的情况下，未经优化的KV缓存所需内存为：2 × 32 × 2,048 × 40 × 5,120 × 2 = 54 GB。

重新设计注意力机制。 这些技术涉及改变注意力机制的工作方式。尽管这些技术有助于优化推理，但由于它们直接改变了模型的架构，只能在训练或微调期间应用。

例如，在生成新token时，局部窗口注意力（local windowed attention）不是关注所有之前的token，而是只关注固定大小的邻近token窗口（Beltagy等人，2020）。这将有效序列长度减小到固定大小的窗口，同时减少了KV缓存和注意力计算。如果平均序列长度为10,000个token，关注1,000个token的窗口可将KV缓存大小减少10倍。

局部窗口注意力可以与全局注意力交错使用：局部注意力捕捉邻近上下文，而全局注意力捕捉文档中的任务特定信息。

跨层注意力（cross-layer attention，Brandon等人，2024）和多查询注意力（multi-query attention，Shazeer，2019）都通过减少键-值对数量来降低KV缓存的内存占用。跨层注意力在相邻层之间共享键和值向量。三层共享相同的键-值向量意味着KV缓存减少三倍。而多查询注意力在查询头之间共享键-值向量。

分组查询注意力（grouped-query attention，Ainslie等人，2023）是多查询注意力的一种推广。它不只为所有查询头使用一组键-值对，而是将查询头分成较小的组，并且仅在相同组内的查询头之间共享键-值对。这使得查询头数量和键-值对数量之间的平衡更加灵活。

AI聊天机器人应用Character.AI分享说，他们的平均对话有180条消息的对话历史（2024年）。由于序列通常很长，推理吞吐量的主要瓶颈就是KV缓存大小。三种注意力机制设计——多查询注意力、局部注意力和全局注意力的交错使用、以及跨层注意力——帮助他们将KV缓存减少了超过20倍。更重要的是，这种显著的KV缓存减少意味着对于它们来说，在服务大批量时内存不再是瓶颈。

优化KV缓存大小。 KV缓存的管理方式对于缓解推理过程中的内存瓶颈以及支持更大的批量大小至关重要，特别是对于长上下文应用。目前正在积极开发许多技术来减少和管理KV缓存。

增长最快的推理框架之一vLLM因引入PagedAttention而广受欢迎，该技术通过将KV缓存划分为非连续块来优化内存管理，减少碎片，并支持灵活的内存共享以提高LLM服务效率（Kwon等人，2023）。

其他技术包括KV缓存量化（Hooper等人，2024；Kang等人，2024）、自适应KV缓存压缩（Ge等人，2023）和选择性KV缓存（Liu等人，2024）。

编写注意力计算的内核。 这种方法不是改变机制设计或优化存储，而是研究注意力分数如何计算，并找出使这种计算更高效的方法。当考虑到执行计算的硬件时，这种方法最为有效。

为特定芯片优化的代码称为内核（kernel）。内核编写将在下一节进一步讨论。

内核与编译器

内核是针对特定硬件加速器（如GPU或TPU）优化的专用代码片段。它们通常用于编写计算密集型例程，这些例程需要重复执行，通常是并行执行，以最大化这些加速器的性能。

常见的AI操作，包括矩阵乘法、注意力计算和卷积操作，都有专门的内核来使它们在不同硬件上的计算更加高效。²³

编写内核需要深入理解底层硬件架构。这包括了解内存层次结构如何组织（如缓存、全局内存、共享内存和寄存器），以及数据如何在不同的层级之间访问和移动。

此外，内核通常使用较低级别的编程语言编写，如CUDA（用于NVIDIA GPU）、Triton（OpenAI开发的用于编写自定义内核的语言）和ROCm（用于AMD GPU）。这些语言允许对线程管理和内存访问进行细粒度控制，但也比大多数AI工程师熟悉的语言（如Python）更难学习。

由于这种入门门槛，编写内核过去是少数人掌握的黑科技。芯片制造商如NVIDIA和AMD雇佣优化工程师编写内核，使其硬件在AI工作负载上更高效，而AI框架如PyTorch和TensorFlow则雇佣内核工程师来优化其框架在不同加速器上的性能。

然而，随着推理优化需求的增长和加速器的普及，越来越多的AI工程师对编写内核产生了兴趣。网上有许多优秀的内核编写教程。这里，我将介绍四种常用于加速计算的技术：

向量化（Vectorization） 对于循环或嵌套循环，不是一次处理一个数据元素，而是同时执行多个在内存中连续的数据元素。这通过减少数据I/O操作来降低延迟。

并行化（Parallelization） 将输入数组（或n维数组）划分为独立的块，可以在不同的核心或线程上同时处理，从而加速计算。

循环分块（Loop tiling） 优化循环中的数据访问顺序以适应硬件的内存布局和缓存。这种优化依赖于硬件。高效的CPU分块模式可能在GPU上效果不佳。

算子融合（Operator fusion） 将多个算子合并为单次传递，以避免冗余的内存访问。例如，如果两个循环操作在同一个数组上，可以将它们融合为一个，减少数据读写次数。

向量化、并行化和循环分块可以广泛应用于不同模型，而算子融合需要更深入地理解模型的具体算子和架构。因此，算子融合需要优化工程师更多的关注。

内核是为特定的硬件架构优化的。这意味着每当引入新的硬件架构时，就需要开发新的内核。例如，FlashAttention（Dao等人，2022）最初主要是为NVIDIA A100 GPU开发的。后来，FlashAttention-3针对H100 GPU推出（Shah等人，2024）。

模型脚本指定执行该模型所需的一系列操作。要在硬件（如GPU）上运行这段代码，必须将其转换为与该硬件兼容的语言。这个过程称为降级（lowering）。将代码降级以在特定硬件上运行的工具称为编译器。编译器桥接了ML模型与其运行的硬件。在降级过程中，只要可能，这些操作都会被转换为专门的内核，以便在目标硬件上更快地运行。

推理服务优化

Inference Service Optimization

大多数服务级优化技术关注的是资源管理。给定固定数量的资源（计算和内存）和动态的工作负载（来自用户、可能涉及不同模型的推理请求），目标是将资源高效分配给这些工作负载，以优化延迟和成本。与许多模型级技术不同，服务级技术不会修改模型，也不应改变输出质量。

批处理（Batching）

降低成本的最简单方法之一是批处理。在生产环境中，你的推理服务可能同时收到多个请求。与其单独处理每个请求，不如将差不多同时到达的请求进行批处理，这可以显著提高服务的吞吐量。如果单独处理每个请求就像每人开自己的车，批处理就像把他们一起放在一辆公交车上。公交车可以运送更多人，但也可能让每个人的行程变长。然而，如果做得巧妙，对延迟的影响可以微乎其微。

三种主要的批处理技术是：静态批处理（static batching）、动态批处理（dynamic batching）和连续批处理（continuous batching）。

最简单的批处理技术是静态批处理。服务将固定数量的输入组成一个批次。就像一辆公交车等待每个座位都坐满才出发。静态批处理的缺点是所有请求都必须等到批次满才能执行。因此批次中的第一个请求会被延迟，直到批次的最后一个请求到达，无论最后一个请求有多晚。

而动态批处理为每个批次设置一个最大时间窗口。如果批量大小为4，窗口为100毫秒，服务器在收集到4个请求或经过100毫秒时处理该批次，以先到者为准。就像一辆按固定时刻表发车或满员即发的公交车。这种方法使延迟处于可控范围，早期的请求不会被后来的请求拖累。缺点在于批次在被处理时可能并非总是满的，可能导致计算资源浪费。静态批处理和动态批处理的可视化如图9-15所示。

在朴素的批处理实现中，所有批次请求必须在完成后才能返回响应。对于LLM，某些请求可能比其他请求花费更长的时间。如果批次中的一个请求只生成10个响应token，而另一个请求生成1000个响应token，短响应用户必须等待长响应完成后才能得到结果。这导致了短请求的不必要延迟。

连续批处理允许批次中的响应在完成后立即返回给用户。它通过选择性批处理那些不会使一个响应的生成拖累另一个响应的操作来实现，如Orca论文所述（Yu等人，2022）。批次中一个请求完成后，其响应被返回，服务可以立即将另一个请求添加到批次中填补其位置，使批处理连续进行。就像一辆公交车，送下一名乘客后，可以立即接上另一名乘客以最大化载客率。连续批处理（也称为动态批次调度）的可视化如图9-16所示。

解耦预填充和解码

LLM推理包括两个步骤：预填充和解码。由于预填充是计算密集型的，解码是内存带宽密集型的，使用同一台机器执行两者可能导致它们低效地竞争资源，显著拖慢TTFT和TPOT。设想一个GPU已经在接近其峰值计算能力的状态下处理预填充和解码。它或许还能处理另一个低计算量的工作（如解码）。然而，向这个GPU添加一个新查询意味着引入一个预填充任务以及一个解码任务。这一预填充任务会消耗现有解码任务的计算资源，从而减慢这些请求的TPOT。

四、为什么会这样：本质是“粒度不匹配”

预填充 解码
Kernel 特征 大、少、计算密集 小、多、带宽密集
运行时长 单个 kernel 长 每个 kernel 极短
对延迟敏感度 影响 TTFT 影响 TPOT

把又大又长的预填充和又小又碎的解码混在一起调度，会互相破坏对方的节奏。这就像高速公路上，一辆大卡车（预填充）和一堆小轿车（解码）混跑——大卡车占道，小轿车频繁变道，整体通行效率反而下降。

推理服务器的一个常见优化技术是分离预填充和解码（disaggregate prefill and decode）。"DistServe"（Zhong等人，2024）和"Inference Without Interference"（Hu等人，2024）表明，对于各种流行的LLM和应用，将预填充和解码操作分配给不同的实例（例如不同的GPU）可以在满足延迟要求的同时显著提高处理请求的数量。尽管解耦需要将中间状态从预填充实例传输到解码实例，但论文表明，在具有高带宽连接（如节点内的NVLink）的现代GPU集群中，通信开销并不大。

预填充实例与解码实例的比例取决于许多因素，例如工作负载特征（如更长的输入长度需要更多预填充计算）和延迟要求（如是否希望更低的TTFT或TPOT）。例如，如果输入序列通常较长且你希望优先考虑TTFT，这个比率可能在2:1到4:1之间。如果输入序列较短且你希望优先考虑TPOT，这个比率可能是1:2到1:1。²⁵

提示缓存（Prompt Caching）

应用中许多提示具有重叠的文本片段。提示缓存（prompt cache）存储这些重叠片段以供重用，因此你只需处理它们一次。不同提示中常见的重叠文本片段是系统提示。没有提示缓存，你的模型需要在每个查询中都处理系统提示。有了提示缓存，系统提示只需为第一个查询处理一次。

提示缓存对于涉及长文档的查询非常有用。例如，如果你的许多用户查询都涉及同一份长文档（如一本书或一个代码库），这份长文档可以被缓存，在多次查询中重复使用。对于长对话也很有用，早期消息的处理结果可以被缓存，并在预测后续消息时重用。

自Gim等人于2023年11月引入以来，提示缓存已被迅速纳入模型API。截至撰写本文时，Google Gemini提供此功能，缓存输入token相比常规输入token享受75%的折扣，但你需要为缓存存储额外付费（截至撰写本文时，每小时每百万token $1.00）。Anthropic提供提示缓存，承诺节省高达90%的成本（缓存的上下文越长，节省越多）和高达75%的延迟降低。提示缓存对不同场景成本和延迟的影响如表9-3所示。²⁶

并行化（Parallelism）

加速器是为并行处理而设计的，并行化策略是高性能计算的支柱。许多新的并行化策略正在被开发。本节仅涵盖少数几种供参考。可以应用于所有模型的两类并行化策略是数据并行（data parallelism）和模型并行（model parallelism）。专门为LLM应用的一类策略是上下文和序列并行（context and sequence parallelism）。一个优化技术可能涉及多个并行化策略。

副本并行（Replica parallelism） 是最直接的策略。它简单地创建你想要服务的模型的多个副本。²⁷ 更多副本允许你同时处理更多请求，但代价是使用更多芯片。将不同大小的模型适配到不同芯片上是一个装箱问题（bin-packing problem），随着模型数量、副本数量和芯片数量的增加而变得复杂。

假设你有不同大小的模型混合（例如8B、13B、34B和70B参数），并可访问不同内存容量的GPU（例如24 GB、40 GB、48 GB和80 GB）。为简单起见，假设所有模型使用相同的精度（8位）：

  • 如果你有固定数量的芯片，需要决定为每个模型创建多少个副本以及使用什么GPU来最大化你的指标。例如，是将三个13B模型放在一个40 GB GPU上，还是将这个GPU保留给一个34B模型？
  • 如果你有固定数量的模型副本，需要决定获取什么芯片以最小化成本。然而，这种情况很少发生。

通常，你的模型太大，无法放入一台机器。模型并行（Model parallelism）指的是将同一模型拆分到多台机器的实践。将模型适配到芯片上，在模型并行的情况下会变得更加复杂。

拆分模型有几种方式。推理中最常见的方法是张量并行（tensor parallelism），也称为算子内并行（intra-operator parallelism）。推理涉及对多维张量的一系列算子操作，如矩阵乘法。在这种方法中，算子涉及的张量被划分到多个设备上，有效地将该算子分解为更小的部分并行执行，从而加速计算。例如，在乘以两个矩阵时，可以将其中一个矩阵按列拆分，如图9-18所示。

张量并行有两个好处。首先，它使服务无法容纳在单台机器上的大型模型成为可能。其次，它减少了延迟。然而，延迟优势可能会因额外的通信开销而减少。

另一种拆分模型的方式是流水线并行（pipeline parallelism），涉及将模型的计算划分为不同的阶段，并将每个阶段分配给不同的设备。数据流经模型时，每个阶段处理一个部分，而其他阶段处理后续部分，使得计算可以重叠。图9-19显示了在四台机器上的流水线并行的样子。

虽然流水线并行使得在多台机器上服务大型模型成为可能，但由于流水线阶段之间额外的通信，每个请求的总延迟会增加。因此，对于延迟要求严格的应用，通常避免使用流水线并行，而倾向于副本并行。然而，流水线并行在训练中很常见，因为它有助于提高吞吐量。

两种不那么常见但值得一提的技术是上下文并行（context parallelism）和序列并行（sequence parallelism），它们都是为了更高效地处理长输入序列而开发的。在上下文并行中，输入序列本身被拆分到不同的设备上单独处理。例如，输入的前半部分在机器1上处理，后半部分在机器2上处理。在序列并行中，整个输入所需的算子被拆分到多台机器上。例如，如果输入需要注意力计算和前馈计算，注意力可能在机器1上处理，而前馈在机器2上处理。

总结

Summary

模型的可用性在很大程度上取决于其推理成本和延迟。更便宜的推理使AI驱动的决策更经济实惠，而更快的推理使AI能够集成到更多应用中。鉴于推理优化的巨大潜力，它吸引了许多优秀人才，他们不断提出创新方法。

在开始提高效率之前，我们需要了解效率是如何衡量的。本章从常见的效率指标开始，包括延迟、吞吐量和利用率。对于基于语言模型的推理，延迟可以分解为首token时间（TTFT），受预填充阶段影响；以及每个输出token时间（TPOT），受解码阶段影响。吞吐量指标与成本直接相关。延迟和吞吐量之间存在权衡。如果你能接受更高的延迟，就可能降低成本；而降低延迟通常会增加成本。

模型运行的效率取决于其运行的硬件。因此，本章还提供了AI硬件的概览，以及在不同加速器上优化模型所需的条件。

本章接着讨论了推理优化的不同技术。鉴于模型API的可用性，大多数应用开发者会直接使用这些API及其内置优化，而不是自己实现这些技术。虽然这些技术可能并非对所有应用开发者都直接相关，但我希望本章阐述的优化思路——识别瓶颈然后解决它们——能够帮助你诊断应用中的延迟和成本问题。
