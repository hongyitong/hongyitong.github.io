2.3 了解硬件需求与建议

Understanding hardware needs and recommendations

你可能听说过训练LLM非常昂贵。对于领先的LLM公司来说，在低端花费100万到1000万美元，高端花费超过5000万美元的计算成本来训练一个新的基础模型LLM（在添加任何推理技术之前）并不罕见。

例如，DeepSeek V3模型（作为DeepSeek R1推理系统的基础检查点）在2,048个NVIDIA H800 GPU上训练了约11周，估计成本为550万美元。（DeepSeek V3是少数几个完全透明公开计算成本的近期模型之一。）根据技术报告，最终训练运行使用了1,480万GPU小时的计算量。能耗约为620 MWh，大约相当于一个美国家庭55年的用电量。

如此巨大的资源需求和高昂的价格，使得我和大多数读者无法自行开发LLM。相反，我们将使用一个相对较小（但功能强大）的预训练LLM，并在此基础上实现推理技术。这个较小的LLM是当代最先进模型的缩小版，但遵循相同的架构。我们将应用的推理方法与大型LLM使用的相同。区别在于，较小的LLM让我们能够以预算友好的方式探索这些方法。

打个比方，想象你好奇汽车是如何工作的。如果你是汽车新手，可能不会一开始就制造一辆昂贵的法拉利。相反，你会从一辆更基本的汽车开始，比如大众甲壳虫，它仍然能教会你很多关于发动机和变速箱的工作原理。事实上，我甚至认为，在一辆更简单的汽车上工作，反而能让你更好地理解发动机和变速箱的工作原理，因为它没有昂贵汽车那些复杂的精加工。

如输出所示，原始文本被分割为六个TokenID。每个Token代表一个词或子词，具体取决于分词器如何分割输入。例如，“Explain"被拆分为两个单独的Token"Ex"和"plain”。这是因为分词器算法使用了一种基于子词的方法，称为字节对编码（BPE）。BPE可以使用全词和子词单元的组合来表示常见词和罕见词。空格也经常包含在Token中（例如" large"），这有助于LLM检测词边界。

Qwen3Tokenizer的词汇量约为151,000个Token，这在目前来说相对较大（作为对比，早期的GPT-2词汇量约为50,000个Token，Llama 3的词汇量约为128,000个Token）。

语言模型中更大的词汇量会增加模型的大小，因为嵌入层和输出层必须存储更多的Token表示。它还会增加生成下一个Token概率的单Token计算成本。更大的词汇量也允许更多单词表示为单个Token，而不是被拆分为子词组件，这可以减少序列长度。例如，将"Explain"这样的词拆分为"Ex"和"plain"会导致更多的输入Token。更多的Token意味着更长的输入序列，这会增加处理时间和资源使用。这之间的权衡是：较大的词汇量具有较高的单Token成本，而较小的词汇量通常会产生更长的Token序列。例如，序列中的Token数量翻倍，大致会使运行模型的计算成本翻倍，因为模型需要处理和生成更多的Token。

遗憾的是，分词器及其实现的细节超出了本书的范围。如果你感兴趣，可以在附录A中找到更多资源，包括我的从头实现。

个人住：

上述这段话主要表达了书中采用的一种从底层手写代码实现大模型（Qwen3）的教学或实践方式。其核心含义可以拆解为以下四个方面：

  • 纯 PyTorch 编写，不依赖第三方库：代码没有使用诸如 Hugging Face Transformers、vLLM 或 Megatron-LM 等现成的重量级大模型框架，而是完全用基础的 PyTorch 算子（如矩阵乘法、激活函数等）从头搭起了 Qwen3 的网络结构。这让读者能彻底看清大模型内部的每一个计算细节。
  • 高可读性与可修改性：因为没有被封装在复杂的黑盒框架里，代码结构非常直观。它的设计初衷就是为了方便开发者在此基础上进行魔改、做学术实验或添加新的模型组件。
  • 兼容官方预训练权重：虽然是自己从零写的“山寨版”架构，但它的张量维度、层级命名和算法逻辑与官方的 Qwen3 完全一致。因此，你可以直接把官方发布训练好的模型权重（Weights）无缝加载到这个自定义的代码里跑起来，而不需要重新训练。
  • “从零开始”的构建精神：强调知其然更知其所以然，通过亲手实现核心代码来真正掌握大模型底层的运行机制。

Q：那么说，市面上的开源大模型只需开发权重，以及对应的架构说明，其它人就可以重用该模型了？

是的，你的理解非常准确。

在开源大模型生态中，“代码/架构”与“权重（Weights）”构成了模型能够被复用的两个核心要素。只要这两者齐备，任何人或社区就可以在本地或云端把这个模型复现并跑起来。

具体而言，这个复用和开源的过程包含以下几个关键点：

  • 架构定义行为，权重决定能力：

    • 架构说明/代码（如模型的配置文件 config.json、网络结构代码）定义了模型的骨架——比如它是几层、注意力机制怎么做、用的什么激活函数。
    • 权重文件（通常是 .safetensors 或 .bin 格式的庞大矩阵文件）则是在海量数据上训练出来的“灵魂”，里面包含了亿万个参数的具体数值。光有架构没有权重，模型就像一个空壳，不会任何知识；光有权重没有架构代码，就像一堆乱码，计算机不知道该怎么把这些数字组织起来计算。

  • 统一的生态标准（如 Hugging Face 规范）：

    目前开源界（如 Meta 的 Llama、阿里 Qwen、Mistral 等）大多遵循一套成熟的标准化接口。官方通常会开源标准的推理代码，并把权重上传。社区开发者甚至不需要像这段话里那样“从零手写”整个架构，只需直接调用现成的库（如 transformers）加载权重就能直接使用。

  • 生态繁荣的基石：

    这种“开源权重 + 公开架构”的模式，催生了极其繁荣的下游生态。比如：

    • 二次开发：开发者可以在官方权重的基础上进行微调（Fine-tuning），让它适应医疗、法律等垂直领域。
    • 量化压缩：社区可以通过 GGUF、AWQ 等技术把大模型压缩，让它能在普通的个人电脑甚至手机上运行。
    • 学术研究与魔改：就像这段话提到的那样，研究人员可以自己用 PyTorch 重写架构，用来做可解释性研究、长文本外推实验或修改底层注意力机制。

简而言之，开源大模型通过“代码+权重”的双轨制，让全球的开发者和研究者都站在了同一个起点上，这也是大模型技术能够以极高速度爆发的重要原因。

文本生成与推理术语

在阅读 LLM 文献或软件文档时，你经常会看到"推理"（inference）一词出现在你可能预期为"文本生成"的地方。在神经网络上下文中，推理有非常具体的含义：即使用一个参数已经学习并固定的模型，运行前向传播并产生预测（例如，生成下一个 token）。在这个阶段，没有任何参数被估计或学习。在前向传播中，我们只是应用一个函数。

这与统计学中的推理不同，后者的目标是从数据中学习未知信息。统计推断涉及估计参数、量化不确定性、或检验关于总体或数据生成过程的假设。

需要注意的是，虽然在大型语言模型上下文中，模型计算的是下一个 token 的分布，人们有时会说模型在"估计"或"推断"下一个 token，但这并非统计学意义上的估计。在这个阶段，模型是一个固定的函数，其参数已经学习完毕。

因此，当我们调用 generate_text_basic_stream 函数时，我们并未执行统计推断。我们执行的是神经网络推理，这仅仅是对训练好的模型进行前向应用，以产生下一个 token 的分布，并从中选择下一个要生成的 token。

如图 2.15 所述，一种提高文本生成速度的工程技巧是 KV 缓存，其中 KV 指模型注意力机制中使用的键（Keys）和值（Values）。如果你不熟悉这些术语，没关系。其核心思想是，我们可以缓存某些中间值，并在文本生成的每一步重复使用它们，如图 2.16 所示，这有助于加速推理。

KV 缓存的核心思想，如图 2.16 所示，是将每次迭代中计算的中间值存储在缓存中。以前，网络生成的每个新 token 都会被拼接到整个输入序列中，并反复送回模型（图中用打叉的框表示）。这种方法效率低下，因为除新生成的 token 外，所有 token 在后续迭代中都保持不变。通过使用 KV 缓存，我们避免了冗余计算，而是直接检索已存储的中间表示。

图 2.16 KV 缓存如何提高自回归文本生成效率的示意图。KV 缓存存储中间表示，而不是在每一步重新处理整个输入序列，这样 LLM 就可以重复使用它们来生成下一个 token。这消除了在后续每次迭代中都将生成的 token 与先前输入拼接的需要。

粗略来说，不使用 KV 缓存生成 n 个新 token 需要反复重新计算越来越长序列上的工作，总计约为 $O(n^2)$ 的解码工作量。这里 $O(n^2)$ 表示总工作量大致随输出长度的平方增长。使用 KV 缓存后，在初始前向传播之后，每个新步骤只处理新添加的 token，将其减少到大约 $O(n)$，这意味着总工作量大致与生成的 token 数量成正比。

如前所述，用于提高 token 生成速度的非推理聚焦的 LLM 细节（如 KV 缓存）不在本书的讨论范围内，也不是本书后面所涉及主题的必要前提。但是，感兴趣的读者可以在我的免费文章中了解更多关于 KV 缓存机制的信息：Understanding and Coding the KV Cache in LLMs from Scratch（https://magazine.sebastianraschka.com/p/coding-the-kv-cache-in-llms）。

如表 2.1 所示，NVIDIA GPU 提供了最佳性能，这是意料之中的。启用 KV 缓存和编译模型后，CPU 的性能仍然出奇地好。然而，有几个重要的细节可以解释为什么在这种特定设置下 GPU 的收益并不更大。

首先，本章中的模型并未针对 GPU 进行优化。该实现旨在兼顾内存使用和计算速度之间的良好平衡，因为内存是大多数读者的主要瓶颈。针对 GPU 优化的变体会预先分配完整的上限为最大上下文长度的 K 和 V 张量（在本例中为 4 万个 token）。这种预分配避免了通过 torch.cat 重复拼接，但也会增加内存消耗。

在较大的上下文大小下，为 K 和 V 分别预分配 4 万个条目会带来显著的内存占用。另一种方法是在构建时让用户指定固定的上下文大小，但这引入了额外的配置开销。这里的 KV 缓存通过 torch.cat 按需增长，这种方法更简单且对内存更友好，尽管在 GPU 上拼接未预分配的张量会稍慢一些。

我在补充材料中包含了一个 GPU 优化版本，其中 KV 缓存变体比常规版本略快，但使用了更多内存（参见 https://github.com/rasbt/reasoning-from-scratch/tree/main/ch02/03_optimized-LLM）。

其次，用于基准测试的模型较小。较大的模型从 KV 缓存和 GPU 优化内存布局中获益更多。批处理推理也是如此，GPU 可以更好地饱和其计算单元。对于更大的模型或更注重 GPU 的实现，NVIDIA GPU 的性能优势会更加明显。

总结

  • 使用 LLM 生成文本涉及多个关键步骤：

    • 设置编码环境以运行 LLM 代码并安装必要的依赖项

    • 加载预训练的基础 LLM（例如 Qwen3 0.6B），该模型将在后续章节中扩展推理能力

    • 初始化并使用分词器，它将文本输入转换为 token ID，并将输出解码回人类可读的形式

  • LLM 中的文本生成遵循顺序式（自回归）过程，模型一次生成一个 token，通过预测下一个最可能的 token 来实现。
  • 文本生成的速度和效率可以通过以下方式提高：
    • KV 缓存，它存储中间状态以避免在每一步重新计算先前遇到的输入 token
    • 使用 torch.compile 进行模型编译，优化运行时性能
  • 本章通过实现一个使用预训练基础 LLM 的功能性、高效的文本生成流水线，为后续章节中推理能力的学习奠定了技术基础。
